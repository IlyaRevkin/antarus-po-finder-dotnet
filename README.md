# Antarus ПО Finder (.NET / WPF)

[![CI](https://github.com/IlyaRevkin/antarus-po-finder-dotnet/actions/workflows/ci.yml/badge.svg)](https://github.com/IlyaRevkin/antarus-po-finder-dotnet/actions/workflows/ci.yml)

Десктопное приложение для управления базой прошивок и параметров промышленных контроллеров
(ПЛК/УПП/ПЧ) — поиск нужной прошивки по названию шкафа, загрузка новых версий с автоматическим
определением контроллера, хранение параметров ПЧ/УПП, административная панель для настройки
иерархии оборудования.

Это переписывание на .NET 8 / WPF более раннего прототипа на Python (PySide6 + SQLite). Общей
истории коммитов с тем прототипом нет — это независимый репозиторий, архитектура и часть
поведения совпадают намеренно (для паритета функций), часть — сознательно упрощена или изменена
(см. «Отличия и известные ограничения» ниже).

## Архитектура

Три проекта:

| Проект | Назначение |
|---|---|
| `AntarusPoFinder.Core` | Вся бизнес-логика и данные: SQLite (`Database`), доменные модели, иерархия оборудования (`HierarchyService`), поиск (`SearchService`), вся транзакция загрузки прошивки — резолв номера версии, копирование файлов, changelog, вложения, автоопределение контроллера по PSL/KINCO (`FirmwareUploadService`, использует `PslInspector`), файловые операции (`FileSystemHelpers`, `ArchiveExtractor`). Никакого UI — можно было бы переиспользовать под другой интерфейс. |
| `AntarusPoFinder.App` | WPF UI: страницы (Поиск / Осмотр / Модерация прошивок / Загрузка / Параметры / Паспорта шкафов / Сетевые диски / Тикеты / Настройки), диалоги, темизация. |
| `AntarusPoFinder.Tests` | xUnit-тесты: смоук/юнит-тесты слоя `Core` (`Database`, иерархия, парсинг версий, конфликты синка) плюс полные двухмашинные end-to-end прогоны через реальный `ConfigSyncService`/`TicketSyncService` из `App`. Все фикстуры — временные БД/папки, создаваемые и засеваемые каждым тестом самостоятельно (`TestHelpers/TempDb`, `TempRoot`, `TwoMachines`), никакой тест не зависит от файлов на конкретной машине разработчика. Прогоняются в CI на каждый push/PR в `master` (`.github/workflows/ci.yml`). |

Страницы реализованы как обычные `UserControl` с code-behind (без ViewModel на страницу) —
конструктор принимает `AppServices` (доступ к `Database`/`ConfigService`/`HierarchyService`) и
`IAppHost` (аналог «ссылки на главное окно»: статус-бар, индикатор фоновой работы, перезапуск
таймера синхронизации, обновление сайдбара, смена роли). Диалоги — отдельные `Window` с тем же
подходом.

### Фоновые операции и индикатор занятости

Всё, что ходит на сетевой диск, выполняется **вне потока интерфейса** и **видимо**. Раньше было
наоборот: обход диска, чтение общего конфига, копирование прошивок и создание сотен папок шли прямо
на потоке UI и молча, поэтому окно переставало отвечать — неотличимо от «программа зависла».

Соединение SQLite одно на всё приложение и не потокобезопасно, поэтому просто обернуть операцию
целиком в `Task.Run` нельзя: фоновая синхронизация и любой клик пользователя полезли бы в одно
соединение одновременно. Вместо этого каждая операция «БД → диск» разбита на три отделимые фазы:

| Операция | БД: план | Диск (фон) | БД: запись |
|---|---|---|---|
| Структура папок | `HierarchyService.PlanStructure` | `ApplyStructurePlan` | — |
| Досмотр версий на диске | `PlanFwSync` | `ScanFwDisk` | `ImportFwCandidates` |
| Скан неизвестного | `SnapshotNames` | `ScanUnknownFiles(root, names)` | — |
| Загрузка прошивки | `FirmwareUploadService.Prepare` | `CopyFiles` | `Register` |
| Общий конфиг | — | `ConfigSyncService.CheckForUpdateAsync` / `ExportAsync` | `ApplyAsync` |

Однофазные методы (`EnsureStructure`, `SyncFwFromDisk`, `ScanUnknownFiles(root)`, `Upload`, `Export`)
никуда не делись — остались обёртками над теми же фазами и по-прежнему нормальный способ вызова
там, где блокировать некого (тесты, любой не-UI код). Что дисковые фазы действительно не трогают
базу, проверяется в тестах прямо: они прогоняются на **закрытом** соединении (`BackgroundPhaseSplitTests`).

Видимая часть — **два разных индикатора внизу окна**, и это разделение намеренное (жалоба
«отделить анимацию синхронизации конфига от анимации поиска»: раньше обе работы делили одну
полоску, и во время поиска снизу висел текст про синхру).

- `BusyTracker` — полоска с текстом: **видимая работа страницы** (поиск и его обход диска,
  копирование версии, загрузка на диск, сборка PDF), с процентами там, где число шагов известно.
- **Пилюля синхронизации** (`IAppHost.BeginSync`, `SyncStatusState` в `MainWindowViewModel`) —
  скруглённые стрелки ⟳ слева от «Диск: …»: крутятся, пока идёт синхронизация (конфиг, тикеты,
  приём справочника и прошивок, отправка на диск), в подсказке — что именно синхронизируется;
  оранжевый ⚠ — последняя синхронизация не удалась (текст ошибки в подсказке, повтор автоматический);
  стрелки акцентом с надписью «К отправке» — есть неотправленные правки/тикеты; приглушённые
  стрелки — всё синхронизировано. Клик открывает «Сетевые диски».

Пока идёт работа, в полоске написано, что именно («Обновление прошивки: …»,
«Готовим PDF инструкции…»), с процентами там, где число шагов известно заранее. Несколько
операций одновременно — показывается последняя начатая, остальные счётчиком «+N». Кнопки, у которых
повторный клик запустил бы вторую такую же работу («Синхронизировать сейчас», «Загрузить»,
«Обновить все»), гаснут на время своей операции; фоновый тик синхронизации, пришедший поверх ещё не
закончившегося предыдущего, просто пропускается.

## Модель данных и иерархия

Прошивки и параметры организованы по 4-уровневой иерархии:

```
ПО/{Группа}/{Подтип}/{Контроллер}/{версия}/файл
ПО/{Группа}/{Подтип}/Паспорт/{название паспорта}/файл
Параметры/{Группа}/{Подтип}/{Производитель}/файл
```

- **Группа** — тип шкафа верхнего уровня (НГР — насосная, ПЖ — пожарное водоснабжение, ТГР —
  тепловая); у каждой свой числовой префикс версии.
- **Подтип** — КПЧ/ВЗУ/КНС/ПП/ХП/FD и т.д.; подтип `—` означает «подтипа нет» (папка
  пропускается, актуально для ТГР).
- **Паспорт** — папка «Паспорт» принадлежит подтипу (лежит рядом с «ОПЦ», а не внутри папки
  контроллера): паспорт описывает **шкаф**, а не программу ПЛК, и у части шкафов прошивки нет вовсе.
  Внутри — по подпапке на каждый паспорт, чтобы у одного подтипа могло быть несколько исполнений с
  одинаковым именем файла.
- **Контроллер** — модель (SMH4/SMH5/KINCO/PIXEL2/PIXEL), у каждой — список **модификаций**
  (например PIXEL2-1020, PIXEL2-1321) со своим `hw_version`.
- **Версия прошивки** — строка формата `eq_prefix.sub_prefix.hw_version.sw_version.ГГГГММДД_ЧЧММ`,
  например `2.1.0042.1.20260714_1530`. `hw_version` дополняется нулями до **4 цифр** (SMH4 → `0004`,
  SMH5 → `0005`, а у пикселей номер платы и так четырёхзначный — Pixel2 1321 → `1321`). `sw_version` —
  счётчик, автоматически увеличивается на единицу при каждой новой загрузке для той же тройки
  (подтип, контроллер, hw_version).

Обе стороны (диск и БД) должны совпадать: `HierarchyService.EnsureStructure` создаёт на диске
недостающие папки по данным из БД, `SyncFwFromDisk` — наоборот, добавляет в БД записи о версиях,
физически найденных на диске, но отсутствующих в базе.

**Досмотр диска идёт сам, тем же периодическим тиком, что и остальная синхронизация.** Раньше он
вызывался только внутри применения нового общего конфига, а конфиг **отправляет** лишь
администратор и по умолчанию не отправляет вовсе (`config_push_interval_min = 0`) — то есть у
большинства машин обход диска не запускался никогда. Отсюда и жалоба «позагружал прошивки на компе
коллеги, у себя не вижу»: файлы на диске были, показать их было некому. Что доезжает вместе с
версией:

- **описание и типы пуска** — из `CHANGELOG.md` в папке версии;
- **теги** — оттуда же (разделитель `; `, поэтому многословный тег переживает дорогу целиком) и
  заодно попадают в справочник тегов, иначе версия находилась бы только по названию папки;
- **нестандартные (ОПЦ) версии** — читаются обе раскладки. В новой (этап 5) «ОПЦ» лежит **внутри
  папки контроллера**, а её подпапки названы номером заявки и заводским SN (`01312_SN00042`):
  контроллер известен из пути, гадать по `hw` больше не нужно, заявка и SN разбираются из имени папки,
  а номер версии берётся из `CHANGELOG.md`. В прежней (одна «ОПЦ» на подтип, рядом с папками
  контроллеров) всё работает как раньше: контроллер выводится из `hw_version` в номере версии
  (незнакомый или неоднозначный `hw` — версия пропускается: завести её не тому контроллеру хуже, чем
  не завести вовсе), а заявка и SN восстанавливаются из имени файла.

## Возможности по страницам

### Поиск

Токенизированный полнотекстовый поиск по иерархии: запрос нормализуется (разделители `,;-/\`
схлопываются в пробелы, приводится к верхнему регистру), затем каждая прошивка в БД получает
очки — по числу совпавших частей иерархии (группа/подтип/папка-подтипа/контроллер, только если
длина ≥ 2 символов), плюс ×2 за каждое совпавшее слово из тегов записи и столько же за **тип
пуска**, отмеченный галочкой при загрузке версии (`launch_types`). Тип пуска сравнивается **целым
значением**, а не подстрокой, и независимо от галочки «точное совпадение слова»: список закрытый
(УПП/ПП/ПЧ/КПЧ/Отсутствует) и почти каждое значение в нём — подстрока другого, поэтому запрос
«НГР ПЧ» иначе поднимал заодно шкафы с КПЧ. Из всех версий одного и того же (подтип, контроллер)
в выдачу попадает только версия с максимальным очком, финальный список сортируется по убыванию
очков.

Тег — это **целый тег**, а не слово из него. Тегом бывает полное название шкафа («шкаф управления
пожарными насосами Антарус ПЖ-ПП-2-…»), а строка тегов в БД исторически разделяется пробелом, и
такой тег рассыпался на слова при первом же сохранении. Пробел внутри тега кодируется
(`TagString`), формат строки не поменялся — старые однословные теги читаются как читались. Из этого
следуют два правила выдачи:

- запрос, совпавший с тегом **целиком**, весит больше любого набора отдельных слов;
- галочка **«точное совпадение слова»** означает ещё и «**все** слова запроса, а не любое из них».
  Раньше хватало одного совпавшего слова: нужная версия шла первой, а следом — всё, что случайно
  совпало словом «шкаф». Наладчик, поставивший галочку и вбивший точное название шкафа, получает
  ровно ту прошивку, которой этот тег проставили.

**Шаблонные теги (звёздочка).** Одна прошивка подходит десятку шкафов, отличающихся только амперажом:
«…АМПЕРУС ПЖ-ПП-2-(9-14А)-АВР-FD-Ст», «…-(20-25А)-…». Вместо десятка почти одинаковых тегов ставится
один, со звёздочкой вместо меняющейся части: `Шкаф управления пожарными насосами АМПЕРУС
ПЖ-ПП-2-(*-*А)-АВР-FD-Ст`. Звёздочка подставляет **любую последовательность любых символов** — цифры,
буквы, пробелы (в названиях меняется не только ампераж, но и исполнение), в том числе пустую. Работает
в обе стороны: наладчик вводит конкретное название своего шкафа и находит прошивку с шаблонным тегом,
программист ищет по шаблону и находит прошивки с конкретными названиями. Сверяется **весь запрос
целиком** с **целым тегом** (см. `Core/Services/TagPattern.cs`) — иначе тег, начинающийся со звёздочки,
совпадал бы с чем угодно; частичный ввод при этом ничего не теряет, его как и раньше подхватывает
обычный поиск по словам. На скорости поиска это не сказывается: тег без звёздочки отсеивается одной
проверкой `IndexOf('*')`, никаких регулярных выражений и никакого перебора всех тегов на каждый запрос.
Короткая подсказка про звёздочку стоит прямо под редактором тегов (загрузка, модерация, теги
параметров).

**Конфигурации шкафов.** Одна и та же программа ПЛК обслуживает шкафы, различающиеся только
комплектацией: два насоса; два насоса плюс жокей и одна задвижка; задвижек нет вовсе. Прошивка при
этом физически одна — отличается только название шкафа, по которому её ищет наладчик
(`…ПЖ-ПП-2-(9-14А)-АВР-FD-Ст` против `…ПЖ-ПП-2-(24-32А)/Пд-(6А)/Зд1(4А)-АВР-FD-Ст`). Поэтому
программист **заранее заготавливает варианты**: в модерации прошивки открывается блок «Конфигурации
шкафов», куда список названий вставляется целиком — **одна строка = одна конфигурация** (нужно
короткое имя — `Имя | тег; тег`). Звёздочка работает и здесь: `…ПЖ-ПП-2-(*-*А)-АВР-FD-Ст` одной
строкой закрывает весь ряд амперажей.

Конфигурация — это **отдельная запись** `fw_versions` с тем же `disk_path` и `version_raw`, что у
самой прошивки, непустым `config_name` и своим набором тегов. **Файлы на диске не копируются никогда**:
шара WebDAV и медленная, а вариантов у одной прошивки бывает десяток — десять копий одних и тех же
байт означали бы и десятикратную заливку, и риск, что копии разойдутся. Тем же приёмом давно живут
копии прошивки под другие подтипы шкафа, и весь код вокруг его понимает: файлы не удаляются, пока на
них ссылается хоть одна запись, вывод из модерации снимается со всех записей разом, удаление уезжает
надгробием. В выдаче поиска вариантов **не видно как десяти одинаковых прошивок**: выдача и так отдаёт
одну строку на пару подтип+контроллер, с максимальным рангом, — то есть ту конфигурацию, чьи теги
совпали с запросом (на общем запросе, где комплектация не спрашивалась, наверх выходит сама прошивка).
Очередь модерации и история версий конфигурации не показывают вовсе — это не отдельные версии.
Обновили прошивку — весь заготовленный ряд комплектаций **переезжает на новую версию** вместе с тегами
и HMI-проектом (`FirmwareConfigService.CarryOver`): конфигурации описывают шкафы, а шкафы от
обновления программы никуда не деваются.

**Частота выбора.** Приложение запоминает, какую версию оператор взял по такому же запросу
(`fw_search_usage`: открыл проект/файл, залил в контроллер или скачал локально — просмотр карт,
инструкций и истории не в счёт). В следующий раз по тому же запросу эта версия идёт выше среди
**равно подходящих**, а на карточке написано «по этому запросу выбирали N раз» — иначе подъём
выглядел бы необъяснимым. Вклад частоты ограничен (`MaxUsageBonus`): сто открытий прошивки другого
шкафа не должны вытаскивать её в чужую выдачу — это подсказка среди подходящего, а не замена
релевантности. Таблица локальная: в общий конфиг не выгружается и с других машин не приезжает.

**Фильтры** — отдельная кнопка справа от строки поиска, свёрнута по умолчанию (в строке и так три
кнопки, а фильтры нужны не каждый раз): тип шкафа, подтип, контроллер, тип пуска, тег. Фильтр —
это «показывай только такое», а не «подними повыше»: он применяется **до** подсчёта очков. Поле
тега — с поиском по списку: набранное сужает выпадающий список (у наладчика он длинный), и
предлагаются только теги, реально проставленные на версиях. Пустой запрос **с** фильтрами —
осмысленное «покажи всё такое» (все прошивки НГР на SMH5, все с типом пуска ПЧ). Свёрнутая панель
фильтры не отменяет — поэтому на кнопке стоит точка, когда что-то выбрано, а «Сбросить» очищает и
запрос, и фильтры.

**Снимок для поиска.** Раньше каждый поиск заново вычитывал все `fw_versions` с тремя JOIN'ами — на
каждое нажатие «Найти», на каждое переключение режима, на каждый молчаливый повтор запроса (возврат
на вкладку, тик синхронизации, закрытие диалога тегов). Теперь снимок читается один раз и
переиспользуется, пока данные не менялись. Ревизия данных поднимается в `Exec`/`ExecuteNonQuery` —
то есть в единственных двух местах, через которые проходит любая запись: про инвалидацию нельзя
забыть, добавив новый метод записи. Плюс индексы по колонкам, по которым реально ищут
(`subtype_id, controller_id`, `version_raw`, резервации, параметры) — без них проверка «какие версии
уже есть у этой пары подтип/контроллер» была полным перебором таблицы на каждую папку контроллера.

**Возврат на вкладку выдачу не перезапускает.** Страница живёт в кэше между переходами, и раньше
каждый заход на «Поиск» молча повторял последний запрос — заглянул в Настройки и вернулся, а поиск
улетел заново вместе с обходом папок версий на сетевом диске (на большом диске это заметные секунды
и вторая прогонка счётчиков). Теперь выдача перезапускается, только когда её пометили устаревшей:
после загрузки или отката прошивки (`IAppHost.InvalidateSearchResults`), после применения общего
конфига и обновления прошивок. Обычное переключение вкладок сохраняет карточки и прокрутку.

Каждый результат — карточка. Кнопок со временем стало слишком много для одного ряда, поэтому в
основном ряду остались только те, ради которых карточку и открывают, а всё остальное убрано в меню
**«Ещё»** (всплывающий список под кнопкой).

Под заголовком карточки — строка **«Файлы:»**: что реально лежит рядом с версией (`LFS ✓ · PSL — ·
HMI ✓ · параметры ✓ · карта ВВ ✓ …`). Раньше «есть ли LFS» приходилось выяснять, открыв меню и не
найдя там строки. Прочерк у LFS/PSL показывается только для Segnetics-проектов (`SegneticsProject`)
— у шкафа на KINCO таких файлов не бывает в принципе, и «PSL —» читалось бы как потерянный файл.
Пока идёт обход папки версии, в строке стоит «проверяем папку версии…» — сам обход идёт в фоне
(карточки рисуются сразу, иначе выдача подвисала на каждый результат, читая сетевую папку).

Описания версии на карточке **нет**: это несколько строк changelog'а на каждой карточке выдачи, без
предела по объёму. Читается там, где оно осмысленно — «Ещё» → «История версий», где заодно видно,
чем версии отличаются друг от друга.

Основной ряд — ровно то, ради чего карточку открывают, и **либо открыть, либо залить, но не обе
кнопки сразу**:

- **Загрузить в ПЛК** — первой кнопкой, когда у версии есть `.lfs` или `.psl`. Готовый LFS
  загружается напрямую, PSL собирается и загружается через Segnetics Loader. Если рядом лежат оба
  файла, используется готовый LFS. Тогда «открыть прошивку» уходит в «Ещё».
- **Открыть прошивку ПЛК (.ext)** — во всех остальных случаях. **Расширение написано на кнопке для
  любого проекта**, а не только для `.psl`/`.lfs`: его считает тот самый резолвер
  (`PlcOpenResolver`), который потом и открывает файл, — разъехаться подпись и результат не могут.
  Порядок выбора един для любого вендора: **исполняемый файл, явно указанный оператором**
  (`ExecutableHint`, относительный путь — файл может лежать во вложенной папке) → `.psl` (исходник
  SMLogix: `.lfs` не открывается ничем, кроме лоадера) → программа ПЛК, когда рядом лежит файл
  панели → первый непохожий на сопроводительный файл. Открывается **только из локального кэша**,
  сеть не трогается; если открыть нечего вовсе — показывается папка версии.
- **Открыть HMI проект** — если панель есть (в т.ч. унаследованная от предыдущей версии шкафа).
- **Параметры** — только если для записи есть файл параметров.

Меню «Ещё» разбито на разделы: **Файлы версии** (открыть папку; «Открыть прошивку ПЛК», когда её
вытеснила кнопка заливки; второй файл пары LFS/PSL; обновить локальную копию с диска),
**Документация** (карта in/out, карта modbus, инструкции, паспорт шкафа — печать / открыть /
открыть папку), **Версия** (история версий, «Модерация
прошивки» — только администратору; пункт назван **так же, как страница сайдбара**, потому что
открывает то же самое окно `EditFirmwareDialog`, а два названия у одного окна только путали).
Запасного пункта заливки в меню нет намеренно: заливка предлагается ровно там, где выполнима. Пункт
показывается, **только когда есть что открыть**: раньше «Карта in/out» висела по одному лишь
заполненному пути в базе, и жать было не на что. LFS/PSL признаются существующими только по папкам
**самой** версии — раньше в счёт шли и соседние версии из локального кэша, из-за чего карточка
писала «LFS ✓» там, где его не выкладывали, а в контроллер подставился бы `.lfs` чужой версии.

**Доп. материалы** (пункт того же раздела «Документация», есть, когда к версии что-то приложено —
см. `FwAttachment`) открываются окном со списком: вид, имя файла, комментарий и путь на диске. Из
окна три пути к файлу: **«Открыть»** (как раньше — программой, назначенной для этого типа файлов),
**«Показать в папке»** (проводник с выделенным файлом) и **перетаскивание прямо из списка** в другую
программу. Причина: прошивку ПЛК от поставщика не «открывают» — её кладут в среду разработки
контроллера, перетащив файл мышью, а раньше единственным действием был запуск через оболочку
Windows, и путь к файлу карточка не показывала вовсе. Кнопка по умолчанию — своя у каждого вида:
у прошивки ПЛК (по виду из справочника или по расширению — `ExtraFilesDialog.PrefersReveal`) это
«Показать в папке», у документа — «Открыть». Окно показывается и для единственного файла: выбор
действия нужен и ему. «Открыть» на исполняемом расширении сначала спрашивает — доп. материалы лежат
на общем диске, куда пишут все.

**Документы всегда открываются самые свежие.** Карта ВВ, карта Modbus и инструкция живут в общей
папке рядом с папкой контроллера и обновляются независимо от версий прошивки, поэтому открывается
не документ, приложенный когда-то к конкретной версии, а самый свежий файл этой папки
(`DocFileResolver`; путь, сохранённый у версии, используется, только если он всё ещё указывает на
существующий файл).

**История версий** (двойной клик по строке открывает папку версии) помечает **одну** версию как
текущую, а не всю историю сразу: самая свежая живая — «Текущая» (жирным), остальные — «Заменена»,
откатанные — «Откатана». Версии с другим `hw_version` — это другое аппаратное исполнение шкафа, и
свежая версия под иное железо ничего не заменяет: самая новая версия каждого hw помечается
«Текущая (HW n)», чтобы наладчик со старой платой видел, что актуально ему. Путь к версии — отдельная
кликабельная строка под таблицей (открывает папку), а описание целиком показано в поле над ней,
поэтому одноимённого столбца в таблице больше нет; колонки «Дата»/«Контроллер» выровнены и не
обрезаются. Отдельный столбец **«Обращений»** показывает, сколько раз версию выбирали в поиске (тот
же счётчик, что на карточке результата). Прямо здесь версию можно **править**: **«Сменить
контроллер»** (запись завели не под тем — переезжает только запись в каталоге, файлы на диске
остаются на месте), **«Кол-во обращений»** (задать счётчик выбора этой версии числом) и
**«Откатить» / «Вернуть в активные»** для конкретной версии (одна кнопка работает в обе стороны по
статусу выбранной строки). Кнопки внизу — **«Скачать на этот ПК»** (тянет выбранную версию с
сетевого диска в локальный кэш, чтобы потом залить в ПЛК) и **«Закрепить локально»** (ставит метку
`.keep`, и тогда версия остаётся на этом компьютере, даже если на сетевом диске её сделают
неактуальной или удалят).

**Локальная копия подтягивается сама.** Отдельной кнопки «Синхронизировать» на карточке больше нет:
версии из выдачи, которых ещё нет в `%LocalAppData%\AntarusPOFinder\firmware\<имя>\<версия>`,
копируются с сетевого диска в фоне, а карточка показывает состояние («синхронизируем…» → «✓
локальная копия обновлена» / текст ошибки); общий ход при этом виден и внизу окна, в индикаторе
занятости — карточка может быть уже прокручена за экран. Копирование последовательное (сетевой диск
компании регулярно отваливается, десяток параллельных копий делу не помогает) и прекращается, если
оператор успел запустить новый поиск. За одну выдачу тянется не больше 10 версий — сколько всего нашлось и
сколько взято, видно в строке статуса, остальные копируются вручную через меню «Ещё». Выключается в
Настройки → Общие → «Поиск».

**Локально держатся только актуальные версии.** Чтобы не забивать диск наладчика всей историей,
периодическая синхронизация убирает из локального кэша те версии, которые на сетевом диске стали
неактуальными или удалены — но только **не закреплённые**: разовая копия, взятая кнопкой «Скачать на
этот ПК», уберётся ближайшей синхронизацией, а помеченная «Закрепить локально» (метка `.keep`)
останется. Более старые версии всегда можно вернуть из «Ещё» → «История версий».

Отдельно на панели инструментов: смена/очистка папки осмотра, упрощённый скан документа (запуск
приложения «Сканер Windows» + сравнение содержимого стандартных папок вывода до/после — без
прямого управления сканером через WIA, см. «Известные ограничения»), и загрузка фото с телефона
по QR-коду (см. ниже).

**Режимы поиска.** Переключатель над строкой поиска — что искать: **прошивки** (описано выше),
**файлы параметров** или **электросхемы шкафов** на «втором диске» (путь настраивается на странице
«Сетевые диски»). Схемы ищутся тем же токенизированным алгоритмом, включая галочку «точное
совпадение слова», по всему дереву папок второго диска на любую глубину — годится и шкаф-папка
(`.../ПЖ-101/схема.pdf`, каждый файл внутри — отдельная схема), и файл, названный прямо по имени
шкафа (`.../НГР-205.pdf`). Первый обход дерева на этом диске (самая долгая часть — сетевая шара)
уходит в фон и не блокирует окно; повторные поиски по тому же диску переиспользуют кэш, пока он не
сброшен (смена пути ко второму диску сбрасывает кэш сама).

Обход диска **ровно один** независимо от того, сколько раз нажали «Найти»: он не привязан к запросу,
повторное нажатие только переставляет фильтр выдачи, а не заводит вторую фоновую операцию (раньше
пять нажатий давали пять параллельных обходов одной шары и растущий счётчик занятости). Найденное
показывается **по ходу обхода**, а не после него, и рядом с «Найти» появляется кнопка
**«Остановить»** — увидел нужное, дальше сетевую шару читать незачем; уже показанные карточки
остаются на экране. Прерванный обход кэш не пишет, иначе следующий поиск принял бы обрезанный
список за весь диск. Папка, недоступная по правам («System Volume Information», урезанный ACL),
пропускается — раньше она молча обрывала обход целиком. Автодополнение названий шкафов по
второму диску (например, в других полях формы) не реализовано — сегодня это только поиск и
просмотр самих файлов схем.

Карточка схемы — **«Открыть файл»**, **«Открыть папку»** (папка с выделенным в ней файлом) и путь
целиком. Рисуется не больше `SearchResultCap.MaxCards` (300) карточек за раз — на широком запросе
совпадений десятки тысяч, а карточки лежат в невиртуализованном списке, — остальное дорисовывает
кнопка **«Показать ещё N (не показано: M)»** в конце списка; её счётчик растёт прямо по ходу обхода.

**Фильтры подстраиваются под режим поиска.** У схем свои фильтры — набор галочек **формата**
(PDF / DWG / DXF / JPG / PNG / TIFF / BMP): рядом со схемой в PDF на диске лежит её же исходник DWG и
десяток фотографий шкафа, без этого половина выдачи не о том. Фильтры прошивок (тип/подтип/
контроллер/тип пуска) в режиме схем скрыты — они там ничего не фильтровали и выглядели сломанными.
**Подтипы предлагаются только у выбранного типа шкафа**: раньше список был общий на всю базу, и пара
«тип ПЖ + подтип из НГР» гарантированно давала пустую выдачу.

### Segnetics Loader

Кнопка **«Загрузить в ПЛК»** открывает компактное окно операции, которое **стартует само**: файл уже
выбран карточкой, и второе нажатие «Загрузить» ничего не решало. На виду — имя файла (полный путь в
подсказке), прогресс и строка **«Подготовка ПЛК»**: авто-старт применяет запомненное значение опции
«Форматировать проект и обновить ядро», поэтому оно обязано быть видно до и во время работы. Под
«Дополнительно» — сама галка, выбор другого файла и «Запустить заново»; под «Подробности» — цветной
журнал, который раскрывается сам при ошибке. Внизу максимум две кнопки: «Остановить» во время
работы, «Закрыть» после; «Рабочая папка» и «Сохранить журнал…» — в меню «…», доступном по итогу.
Недоступность Automation показывается сообщением **до** открытия окна, а не мёртвой кнопкой внутри.

Внутри пары LFS/PSL берётся файл, **указанный оператором в модерации** (`ExecutableHint`), а не
первый попавшийся: в папке версии бывает пачка `.lfs` (по одному на шкаф).

**Собранный `.lfs` уезжает в папку версии на сетевом диске**, а не оседает в локальной рабочей
области заливавшей машины — иначе следующий наладчик на другой машине снова видел бы один `.psl`.
Отдельно от заливки `.lfs` можно собрать без ПЛК (действие `build` изолированным SMLogix): сразу
после выкладки версии с одним исходником Searcher предлагает это сделать, а в модерации прошивки
есть кнопка **«Собрать LFS из PSL»**. Сборка идёт локально, на диск копируется только готовый файл и
только через временное имя — оборванная шара оставит `*.lfs.part`, но не битый `.lfs`.

Searcher запускает встроенный `SegneticsLoader.Automation.exe --stdio` и отображает его JSONL-
события `started`, `plan`, `progress`, `log` и терминальный результат. Кнопка «Остановить» отправляет
в тот же процесс команду `cancel`. Подключение к ПЛК, учётные данные и путь к прошивке берутся из
сохранённых настроек Segnetics Loader.

Файл сначала копируется в локальную рабочую область
`%LocalAppData%\AntarusPOFinder\loader\<дата>_<версия>\src`; Loader не читает проект с сетевой
папки во время загрузки. Лог Searcher сохраняется рядом, рабочие области старше 7 дней удаляются
автоматически.

Runtime Loader поставляется в `<папка приложения>\Loader`. Необязательная настройка позволяет
указать другую папку Loader, GUI exe или Automation exe. Полная схема Searcher-интеграции описана в
[`docs/loader-integration.md`](docs/loader-integration.md), внешний API — в
[`docs/loader/LOADER_AUTOMATION_API.md`](docs/loader/LOADER_AUTOMATION_API.md). Для запуска
framework-dependent Automation требуется Microsoft .NET 8 Runtime x64.

### Загрузка

Форма загрузки новой версии прошивки. Вся логика транзакции загрузки (резолв номера версии,
копирование файла/папки и вложений, запись `CHANGELOG.md`, тегирование, исполнение резервации)
живёт в `AntarusPoFinder.Core.Services.FirmwareUploadService` — чистый метод
`Upload(request) → result`, без зависимостей от WPF, покрытый юнит-тестами. `UploadView`
(code-behind) собирает `FirmwareUploadRequest` из полей формы, вызывает сервис и показывает
результат (успех/ошибка/предупреждения); два бывших модальных диалога-подтверждения (неизвестное
расширение, папка версии уже существует) сервис возвращает как `NeedsConfirmation` — `UploadView`
переспрашивает пользователя и повторяет вызов с подтверждённым флагом. Сам `Upload` — обёртка над
тремя фазами `Prepare` → `CopyFiles` → `Register` (см. «Фоновые операции» выше): `UploadView`
вызывает их по отдельности, чтобы копирование гигабайтов на сетевой диск шло в фоновом потоке с
прогрессом внизу окна. Оба подтверждения спрашиваются между `Prepare` и `CopyFiles`, то есть до
того, как на диск записан хоть один байт — отказ пользователя не оставляет следов. Автодетект контроллера по
`.psl`/KINCO-расширению (см. п. 2 ниже) тоже вызывает методы `FirmwareUploadService`, а не хранит
эту логику в code-behind. Четыре поля вложений (Карта in/out, Карта modbus, Инструкция,
HMI-проект) используют общий UI-хелпер `FilePickerRow` (`AntarusPoFinder.App/Views`) для кнопок
«Файл…»/«Папка…»/«Очистить» вместо дублирования диалогового кода в каждом поле.

1. Выбор Типа шкафа (Группы) и Модификации контроллера рядом на одной строке (единый список
   модификаций всех контроллеров, не сгруппированный по моделям), затем — Подтип(ы) отдельной
   строкой ниже (см. п.10).
2. **Автоопределение контроллера по содержимому `.psl`-файла** (см. `PslInspector` в `Core`):
   в бинарном файле проекта Segnetics SMLogix ищутся JSON-фрагмент `"key":"..."` / `"owner":"..."`
   или XML-тег `<device>...</device>`; извлечённый идентификатор (например `PIXEL2-1020-70-4`)
   разбирается регулярным выражением на модель (`PIXEL2`) и модификацию (`1020`), и если в
   справочнике находится точное совпадение — комбобокс переключается сам с пометкой
   «🔍 автоопределено из файла». Никогда не блокирует загрузку и не выбирает ничего насильно.
3. Два независимых переключателя нестандартного шкафа — **«ОПЦ заявка»** (раскрывает поле № заявки,
   суффикс `_(номер)` в имени файла) и **«ОПЦ SN»** (раскрывает поле серийного номера шкафа, суффикс
   `_SNxxxxx`). Наладчик/программист включает и заполняет только то, что реально есть для конкретного
   шкафа — они не обязаны идти парой. Если включён хотя бы один из двух, целевая папка на диске
   становится `ОПЦ` вместо имени контроллера.
4. Проверка **белого списка расширений** — **два независимых списка** (Настройки → Иерархия):
   один для основного файла прошивки ПЛК, другой — отдельно для HMI-вложения (панель оператора).
   Если расширение загружаемого файла не входит в свой список — показывается предупреждение с
   подтверждением; пустой список ⇒ проверка для него отключена целиком. Проверка применяется
   только к одиночным файлам, не к папкам.
5. Живой предпросмотр итогового пути и имени файла на диске, пересчитывается на каждое
   изменение формы (использует «следующий» `sw_version`, реально ещё не занятый).
6. Обязательное поле «Изменения в этой версии» — текст идёт и в поле `description` в БД, и в
   файл `CHANGELOG.md`, который создаётся (перезаписывается) в папке версии в формате:
   ```
   # {версия}
   Дата: {ГГГГММДД_ЧЧММ}
   Тип пуска: {через запятую}
   Теги: {через «; »}

   {текст изменений}
   ```
   Теги — через `; `, а не через пробел: тег бывает из нескольких слов (полное название шкафа).
   Строки «Теги:» может не быть — это файл старого формата, разбор к этому готов.
7. **Имя файла содержит только числовой номер версии** (`eq.sub.hw.sw[.дата_время]`), плюс
   опционально суффиксы `_(заявка)`/`_SNxxxxx` — например `2.1.042.0001.20260715_1824.PSL`. Группа/
   подтип/контроллер в имя файла больше не подставляются (эта правка — более позднего раунда, чем
   пример ниже мог предполагать): они и так видны из пути на диске (`ПО/Группа/Подтип/Контроллер/...`)
   и разбираются обратно из самого номера версии (`FwVersionNumber.Parse`) — вместо этого при
   загрузке они автоматически добавляются как теги (наравне с тегами, которые ввёл оператор), так
   что поиск по тегам продолжает находить файл по тем же словам. Ранее одиночные `.psl`-файлы также
   всегда получали суффикс `_0` (была отсылка к ожиданиям firmware-тулчейна Segnetics) — этот
   суффикс убран; если это в реальности ломает тулчейн — стоит перепроверить перед следующим релизом
   (см. README «Отличия и известные ограничения»).
8. **HMI-проект** — отдельный чекбокс «Добавить HMI-проект» раскрывает свою собственную зону
   drag&drop (с независимыми кнопками «Файл…»/«Папка…»/«Очистить»), для контроллеров, где HMI —
   отдельный проект со своими файлами (например Segnetics, `.fsprj`), не часть основного файла
   прошивки. HMI **не загружается отдельно** — он всегда прикладывается к версии прошивки ПЛК:
   если заполнена только HMI-зона, а основная (файл/папка прошивки) пустая, «Загрузить прошивку»
   покажет явное объяснение вместо попытки загрузить HMI как саму прошивку.

   **`.fsprj` — это папка, а не файл** (`HmiProjectFormat`). У FStudio выбранный файл лишь точка
   входа: модель панели и драйверы лежат рядом. Программа же копировала на диск ровно его одного, да
   ещё переименовывала в `{версия}_hmi.fsprj` — отсюда пустой проект с руганью «модель HMI не
   соответствует текущему программному обеспечению» при целой папке у программиста. Теперь выбор
   `.fsprj` означает выбор **папки**, и она уезжает целиком, имена внутри не трогаются. Исключение —
   `.fsprj` вповалку с прошивкой ПЛК: такую папку не забрать (уехала бы и прошивка), и программа
   говорит об этом сразу при выборе.

   **Загруженные до этого лежат на диске обрубками и сами не починятся.** Кнопка «Открыть HMI
   проект» такую копию молча не открывает: `HmiProjectFormat.IsStrippedCopy` ловит её по имени
   (`{версия}_hmi.fsprj` — имя целиком наше, пользовательский файл так называться не может) либо по
   пустому окружению. Диалог показывает **путь именно той копии и что программа видит рядом с ней**
   (`Neighbourhood`) — без этих строк предупреждение выглядит враньём: у оператора рядом с
   оригиналом всё на месте, речь-то про копию на сетевом диске. Чинится **оттуда же, с карточки**
   («Указать оригинал…» → выбрать исходный `.fsprj` → заберётся вся папка): совет «сходите в
   модерацию» для таких версий не работал — поле «Открывать файл» указывает в папку прошивки, и что
   там ни выбери, открывался всё тот же пустой проект. Старый обрубок при этом удаляется, в том
   числе если лежал в другой папке (общая «HMI» контроллера до перестройки раскладки): иначе рядом
   остаются оба, и коллегам синхронизируется именно пустой.

   **Панель и программа ПЛК обновляются независимо.** У одного шкафа их правят порознь: сегодня
   поправили логику, панель не трогали. Версия, загруженная **без** панели, подхватывает HMI-проект
   последней живой версии этого же шкафа (тот же подтип + контроллер, см.
   `Database.GetLatestHmiForFirmware`) — раньше она оставалась просто без панели, и на карточке
   кнопки «Открыть HMI проект» не было вовсе. Файлы при этом **не копируются второй раз**: путь
   указывает на ту же папку проекта, что и у предыдущей версии. Карточка честно пишет, откуда
   панель: «Открыть HMI проект **(от 3.0.005.0001)**» — не делать же вид, что она собрана вместе с
   этой версией. Загрузка со своей панелью, понятно, ничего не наследует.

   **Теги предыдущей версии переносятся** — по той же логике и по той же паре подтип+контроллер
   (`Database.GetLatestTagsForFirmware`). Теги описывают **шкаф** («шкаф управления пожарными
   насосами АМПЕРУС ПЖ-ПП-2-…»), а не конкретную сборку программы: новая версия ПЛК ставится ровно в
   те же шкафы. Раньше каждая загрузка начинала с чистого листа — программист либо заново набивал
   десяток названий шкафов, либо не набивал, и свежая версия переставала находиться по тем запросам,
   по которым находилась предыдущая. Перенос **виден заранее**: под редактором тегов в форме загрузки
   стоит строка «Перенесутся теги версии X: …», и они же перечисляются в сообщении об успешной
   загрузке. Набранное вручную не перетирается и остаётся первым, унаследованное дописывается в
   конец, повторы (без учёта регистра) схлопываются; откатанные, архивные и удалённые версии
   источником тегов не считаются. Унаследованные теги попадают и в `CHANGELOG.md` рядом с прошивкой —
   значит доезжают и до машин, куда общий конфиг не отправляется.
9. **Доп. файлы** (необязательные, каждый — своя плитка-слот с drag&drop и кнопкой «×» для очистки,
   см. ниже) — Карта in/out (копируется в подпапку контроллера «Карта ВВ»), Карта modbus
   («Карта Modbus»), Инструкция («Инструкция»).
10. **Подтип(ы) — один чек-комбобокс** (`SubtypeMultiSelect`, замена бывших отдельного комбобокса
   подтипа и кнопки «Ещё подтипы…»): **первый отмеченный** становится основным — задаёт номер
   версии, папку на диске и резерв номера; каждый **следующий** отмеченный — дополнительный, ему
   заводится своя запись в `fw_versions` с тем же номером и тем же `disk_path`, а в папку его
   контроллера кладётся **ярлык** (`.lnk`) на папку версии. Файлы на диске не дублируются —
   прошивка, подходящая пяти подтипам, занимает место один раз, но находится поиском под каждым из
   них (`FirmwareUploadRequest.ExtraSubtypes`, `IShortcutCreator`). Если ярлык создать не удалось
   (сетевая папка, отсутствующий `WScript.Shell`), загрузка не отменяется — выводится
   предупреждение, записи уже заведены. Тот же виджет и та же логика — в «Параметрах» (ниже).
   Если файлы версии позже удалили прямо на диске мимо программы, такой ярлык больше не повисает:
   периодическая синхронизация досматривает диск и убирает осиротевшие ярлыки, чьи файлы исчезли
   (`HierarchyService.PruneOrphanedFirmwareShortcuts`) — только когда сетевой корень реально
   доступен, чтобы offline-шара не выглядела как «всё пропало». Настоящую папку версии основного
   подтипа это не трогает.
11. **Набор файлов вместо папки** — в зону drag&drop (и в диалоге «Файл…») основной прошивки и HMI
   можно перетащить/выбрать сразу несколько файлов. Они складываются в одну временную папку
   (`DropStagingService`), и дальше это обычный сценарий «загрузили папку»: те же проверки, тот же
   выбор исполняемого файла, то же копирование целиком. Временная папка удаляется после загрузки и
   при очистке формы. Раньше из набора молча брался первый файл, остальные пропадали без сообщения.
12. **Какой файл в папке «исполняемый»** — если загружается папка, приложение спрашивает, какой файл
   внутри открывать по кнопке в поиске (`PickFileDialog`, двойной клик заходит в подпапки).
   Единственный файл с «родным» расширением во всём дереве подставляется сам
   (`ExecutableHintResolver.AutoDetect`). Подсказку можно переназначить позже — см. «Правка
   прошивки» ниже.
13. **Тип пуска** (обязательный) — чекбоксы, можно выбрать несколько. Пятый — **«Отсутствует»**,
   для шкафов без типа пуска: при его выборе остальные снимаются и блокируются, чтобы не получилось
   записи «отсутствует + прямой» одновременно.
14. **Откат версии** — помечает последнюю активную версию для выбранной тройки (подтип,
   контроллер, hw_version) как откатанную (`status = rolled_back`); следующая загрузка получит
   тот же самый `sw_version` заново. Файлы на диске никогда не удаляются автоматически — это
   единственный механизм отмены.

**Доп. файлы и доп. настройки — один свёрнутый раздел.** Опции версии (штамп даты/времени в
номере, «ОПЦ заявка»/«ОПЦ SN» из п.3), три доп.файла из п.9 и теги — раньше три разных места на
странице, теперь один `Expander`, свёрнутый по умолчанию. Три доп.файла — не строки
label+текстовое поле+кнопки, а **плитки-слоты** (Карта ВВ / Карта modbus / Инструкция) с
drag&drop и кнопкой «×» для очистки, тот же приём, что у зон ПЛК/HMI выше. Цель — компактность:
обязательная часть формы (метаданные, подтипы, тип пуска, описание) и кнопка «Загрузить» должны
помещаться на минимальном размере окна без прокрутки, а всё необязательное — под одним кликом.

**Единая зона ПЛК+HMI (бета).** Программисту и администратору (не наладчику) в Настройки → Общие →
«Загрузка» доступна галочка «Единая зона для ПЛК и HMI»: вместо двух раздельных drag&drop-зон
(п.8 и левая колонка выше) — одна, куда можно кинуть файл/папку прошивки и HMI-проект вместе или по
очереди. Расширение файла определяет, что есть что; если однозначно решить не получилось —
приложение переспрашивает диалогом. Каждая распознанная часть (ПЛК/HMI) показана отдельной строкой
с кнопкой «×» для переназначения. Экспериментальная функция, выключена по умолчанию; раздельные
зоны ПЛК/HMI остаются поведением по умолчанию и продолжают работать как прежде — это ровно тот же
код, просто скрытый, пока единая зона включена.

#### Правка уже загруженной прошивки

Диалог `EditFirmwareDialog` (открывается из карточки поиска, вкладки «Новые версии» и
Настройки → Прошивки) правит не только описание/теги/типы пуска:

- **Доп. файлы** — Карта in/out, Карта modbus, Инструкция и HMI-проект можно **доложить к уже
  загруженной версии**, если файл прислали позже: `FirmwareAttachmentsService` кладёт их ровно
  туда же, куда их кладёт загрузка новой версии, перезаливать версию целиком не нужно. Пустое поле
  убирает ссылку, файлы на диске остаются (папки общие для всех версий контроллера); при замене
  HMI старая папка проекта сносится, а не мержится.
- **Исполняемые файлы** — переназначить, какой файл открывается по кнопкам «Открыть прошивку ПЛК»
  и «Открыть HMI проект» (двойной клик в диалоге выбора заходит в подпапки). Если отдельной папки
  HMI-проекта у версии нет, файл панели выбирается прямо в папке версии — так поддерживается любой
  проект, где программа ПЛК и панель лежат рядом, без отдельного функционала под конкретного
  вендора.
- **Подтипы шкафов** — набор подтипов, которым подходит эта прошивка, правится после загрузки:
  отметить подтип — завести ему запись и ярлык, снять — убрать их (`FirmwareSubtypeLinkService`,
  общий с «Загрузкой ПО», чтобы правка и загрузка не расходились поведением). Раньше подтипы
  задавались только в момент заливки, и ошибка исправлялась лишь повторной загрузкой. Основной
  подтип — тот, в чьей папке лежат сами файлы — отмечен и заблокирован: это не ссылка, а сама
  прошивка. Файлы у связанных записей **общие**, поэтому и зеркалирование удаления при
  синхронизации, и «Удалить прошивку» в Настройках трогают диск, только если на эти файлы больше
  никто не ссылается (`Database.IsDiskPathSharedByOtherVersions`) — иначе отвязка подтипа унесла бы
  прошивку целиком со всех машин.

### Параметры

Загрузка и просмотр файлов параметров ПЧ/УПП, привязанных к (Группа, Подтип, Производитель).
Удаление записи — мягкое (`archived = 1` в БД), файл на диске никогда не удаляется автоматически.
Тот же чек-комбобокс подтипов, что и в «Загрузке ПО» (см. п.10 выше): файл копируется на диск один
раз, а остальным отмеченным подтипам заводится запись с тем же `disk_path` и кладётся ярлык
(`ParamFileLinkService`).

Два отличия от прошивок, оба следуют из природы параметров:

- **Подтипы берутся из всех типов шкафа, а не только из выбранного.** Один и тот же файл параметров
  частотника подходит сразу нескольким типам, тогда как прошивка ПЛК привязана к конкретному
  контроллеру внутри своего типа. Список при этом по умолчанию сужен до выбранного типа (иначе выбор
  типа ничего бы не значил), остальные открывает галочка «Показать подтипы других типов шкафов»
  внутри самого списка; уже отмеченный подтип чужого типа виден всегда и подписан своим типом
  (`SubtypeMultiSelect.SetGroupFilter` — сужение показа, а не пересборка списка, поэтому отметка не
  теряется при переключении типа). Папка на диске берётся у **основного** подтипа, а не из поля «Тип
  шкафа»: основным может оказаться подтип другого типа.
- **Набор подтипов правится у уже загруженного файла** — кнопка «Подтипы» в списке загруженных
  (`EditParamSubtypesDialog` → `ParamFileLinkService.Apply`), ровно как блок «Подтипы шкафов» в
  карточке прошивки. Отметить — завести запись и ярлык, снять — архивировать запись и убрать ярлык;
  сам файл на диске не трогается никогда (он общий), а основной подтип — тот, в чьей папке файл
  лежит — отмечен и заблокирован.

### Паспорта шкафов

Шаблон паспорта — документ, который печатают и вкладывают в сам шкаф. Привязан к **шкафу** (тип +
подтип), а не к версии прошивки, и отсюда всё остальное:

- у шкафа бывают **и прошивка, и паспорт** (ПЖ ПИ) — паспорт не должен быть вложением конкретной
  версии, иначе при следующей перезаливке версии он «отвязался» бы от шкафа;
- у шкафа бывает **только паспорт**, без прошивки вовсе — тогда единственная запись о таком шкафе и
  есть паспорт, и находиться поиском он обязан по ней.

Загружается на своей странице (тип шкафа + подтип + название + файл). Название становится именем
подпапки на диске, поэтому у одного подтипа спокойно живёт несколько паспортов под разные исполнения;
названия конкретных шкафов навешиваются **тегами** — по ним паспорт и ищется.

**Перезаливка** ведёт себя как у файлов параметров: прежняя редакция уезжает в подпапку «Прежние
редакции» под именем «имя (до ГГГГ-ММ-ДД).ext», запись **обновляется** (свежая дата + датированная
строка в описании), а не плодится второй строкой. Открывается всегда актуальная редакция — архивная
подпапка из резолва документа исключена намеренно (файл копируется со своей датой правки, и убранная
в архив редакция вполне может выглядеть «свежее»).

**Печать.** Лучше грузить `.docx`: PDF собирается из него сам и пересобирается, если документ
правили (тот же `PrintableDocActions`, что и у инструкции — Word/LibreOffice, папка только на чтение
→ во временную). Готовый `.pdf` тоже принимается и печатается как есть.

**В поиске** паспорт появляется двумя способами: пунктами «Печать / Открыть / Открыть папку» в
разделе «Документация» карточки прошивки того же шкафа и — если прошивки у шкафа нет — собственной
карточкой в общей выдаче (счётчик показывает паспорта отдельно от прошивок). Между машинами едет как
файлы параметров: `sync_id`, тумбстоун на удаление, объединение тегов, эталонная синхронизация с
предпросмотром («Паспорта шкафов» в списке того, что у получателей исчезнет).

**Типовой бланк** — паспорт, который не ложится ни на один тип и подтип: НКУ, Щит СПЛ, ШР. Такой
документ печатают под конкретный шкаф, вписывая в него название, и «типа шкафа» у него не бывает по
своей природе. Поэтому у записи нет подтипа, а файл ложится не в `ПО\…\Паспорт`, а в **общую папку
диска** (по умолчанию `<диск>\Конфиг\Паспорта`, рядом с наклейками) — там ему не из чего выбирать
тип. Заводится на той же странице флажком «типовой бланк» (списки типа и подтипа при этом гаснут),
отбирается в таблице пунктом «Типовые бланки», а находится поиском **по тегам** — в них и пишут
названия шкафов, которым бланк подходит.

**Печать бланка** — окно «Паспорт по шаблону»: выбрать бланк, вписать название шкафа, Enter. Название
подставляется в **копию** документа вместо метки (по умолчанию `{{Название}}`) — общий бланк на диске
не меняется никогда. Метка ищется по склейке текста абзаца, а не по отдельным `w:t`: Word режет
надпись на прогоны как ему удобно, и по кускам она не находится вовсе (`DocxTemplateFiller`). Если
метки в бланке нет или название не введено — окно спрашивает **до** печати, а не отправляет на бумагу
лист с `{{Название}}`. Бланк не в формате Word (готовый PDF, старый `.doc`) печатается как есть.

Название шкафа подставляется из **поискового запроса**: искали «ЩУН-9», нашёлся бланк по тегу — оно и
стоит в поле (название самого бланка из подстановки выпадает: «НКУ» — вид документа, а не шкаф).
Открыть окно можно из сайдбара (рядом с «Наклейками»), с панели осмотра — шкаф как раз перед тобой, —
со страницы паспортов и из Настройки → Печать. Там же администратор меняет папку бланков и саму
метку; выбранный в прошлый раз бланк остаётся per-machine. Файл, положенный в папку руками мимо
загрузки, окно тоже показывает — папка ведёт себя как папка наклеек.

### Этикетка с QR и наклейки

Две разные вещи, обе настраиваются на вкладке Настройки → **Печать**.

**Этикетка с QR на инструкцию** — кнопка «QR инструкции» в ряду действий карточки прошивки, рядом с
остальными действиями по инструкции. Окно показывает саму этикетку и что зашито в код:

- задан **веб-адрес диска инструкций** — в QR уходит ссылка на файл (базовый адрес + путь от корня
  диска). **Кириллица идёт как есть**: экранируется посегментно и только то, что иначе ломает разбор
  адреса — пробел, `%`, `#`, `?`, `\` (посегментно, а не строкой целиком, иначе слеши-разделители
  уехали бы в кодировку вместе с именами). Раньше каждое имя папки прогонялось через
  `Uri.EscapeDataString`, и одна русская буква становилась шестью символами (`П` → `%D0%9F`): ссылка
  раздувалась почти вдвое, читать её было нельзя, а QR выходил плотнее — на типовом пути 274 байта
  против 162, то есть версия кода 13 (69 модулей) вместо 11 (61). Чем плотнее код, тем крупнее нужна
  наклейка и тем хуже его берёт камера, то есть кодирование било ровно по тому, ради чего этикетка и
  заводится. Адрес с не-ASCII символами — это IRI (RFC 3987), браузеры и сканеры принимают его и сами
  переводят в проценты уже на проводе. Это единственный вариант, который открывается **с телефона**;
- адрес не задан или файл лежит вне диска — в QR уходит **сетевой путь** (`\\сервер\шара\…`): с
  рабочего компьютера откроется, с телефона нет, о чём окно честно пишет.

Ссылка считается от того диска, где файл реально лежит: инструкции могут быть уведены на третий
диск, и путь надо брать от его корня. В QR предпочитается PDF (docx на телефоне бесполезен);
пересборкой PDF из docx печать этикетки НЕ занимается — в отличие от «Печати инструкции», она не
должна на минуту подвешивать оператора запуском Word.

**Наклейку можно печатать до того, как инструкцию написали.** Кнопка «QR инструкции» есть и у версии,
где документа ещё нет: в папке лежит заглушка «Инструкция в разработке» под тем же самым именем, под
которым потом ляжет настоящий документ (см. «Имя файла инструкции и заглушка» ниже), поэтому адрес
постоянный и переклеивать наклейку не придётся. Окно об этом предупреждает прямым текстом.

### Имя файла инструкции и заглушка

**Имя — `инструкция_<версия>.<расширение>`** (`InstructionNaming`), по тому же принципу, что и у файла
прошивки («имя файла = имя папки версии»): по документу, вырванному из контекста, должно быть видно, к
какой версии он относится. Приставка нужна, чтобы в одной папке инструкция и прошивка не оказались
файлами с одинаковым именем и разными расширениями. Расширение приводится к нижнему регистру.

Имя ставится **в момент укладки файла на диск** (`InstructionStorage.Copy` — и загрузка версии, и
догрузка вложения к уже загруженной) и правится **перестройкой диска** (Настройки → Иерархия →
«Перестроить структуру диска…», отдельная галочка, сухой прогон и журнал как у остальных операций,
идемпотентно). Перезаливка копирует новую редакцию сразу по каноническому пути: иначе она легла бы
рядом под именем источника, а по напечатанному QR продолжала бы открываться прошлая редакция.
Переименовываются только инструкции в папке **своей версии**; общая папка «Инструкция» контроллера
принадлежит всем его версиям сразу, приписать её файл одной из них было бы выдумкой. Копия, лежащая
на первом диске рядом с прошивкой, переименовывается вслед за документом на третьем (иначе путь в
базе, который считается заменой корня, указал бы в пустоту), а папки-сканы не трогаются никогда —
путь папки записан у коллег в `fw_versions.instructions_path`.

**Заглушка «Инструкция в разработке»** (`InstructionStub` + `App/Services/InstructionStubWriter`,
этап 1b плана иерархии) — одностраничный PDF, который кладётся в папку «Инструкция», когда документа
там ещё нет: пустая папка неотличима от «инструкцию потеряли». Кладётся во все места, где инструкцию
ищут — при загрузке версии без инструкции, при снятии ссылки на инструкцию в модерации, при проверке
структуры диска (она идёт при каждом запуске) и при перестройке, — и на основном диске, и в зеркале на
диске инструкций.

Три правила, без которых от неё был бы вред:

- **имя у заглушки — то же каноническое**, что у будущего документа. Это и есть смысл затеи: наклейку
  печатают до того, как инструкцию дописали, и настоящий документ ложится ровно на её место. Раз имена
  совпадают, отличаются они по содержимому — строкой-меткой `%ANTARUS-INSTRUCTION-STUB` в конце файла
  (комментарий PDF после `%%EOF`, читалки его игнорируют);
- **заглушка не инструкция**: все резолверы документов пропускают её наравне с ярлыками
  (`DocFileResolver.IsNotADocument`), поэтому отметка «инструкция ✓» на карточке, печать и
  «Редактировать» относятся только к настоящему документу. Единственное исключение — этикетка с QR:
  ей нужен путь, а не документ, и путь этот один и тот же;
- **настоящий документ не затирается никогда**: заглушка пишется только туда, где документа нет ни в
  самой папке, ни в парной к ней на другом диске, ни в виде ярлыка на него; а как только документ
  появляется — уходит сама.

**Вид страницы настраивается** — Настройки → Печать → «Макет заглушки…». Заголовок, пояснение,
подпись внизу, размеры шрифтов, рамка по краю и тон серого; в любую строку можно вставить
`{версия}` — там, где версия неизвестна (общая папка контроллера), подстановка просто исчезает.
Предпросмотр рисуется тем же кодом, что и настоящий файл, поэтому подгонять ничего не приходится
вслепую. Макет общий и синхронизируется: заглушки на хостинг кладут разные машины, а видит их один и
тот же заказчик. Уже созданные заглушки при смене макета не перерисовываются — для этого есть
«Перезалить всё» на странице «Хранилище».

**Инструкция в формате Word на хостинг уходит собранным PDF.** Ссылку под QR открывают на телефоне в
цеху, где `.docx` либо не откроется, либо потянет установку офиса; и путь в хранилище, и ссылка на
наклейке ведут на PDF. Собрать его нечем (нет ни Word, ни LibreOffice) — программа говорит об этом
прямо, а не кладёт на хостинг файл, который потом не открывается.

**Что где стоит на этикетке — настройка, а не вшитая раскладка.** Прямо в окне «QR инструкции», рядом
с предпросмотром (в общих настройках их намеренно нет: полтора десятка ручек без картинки — это
настройка вслепую):

- **положение кода** — «сам» (как было: слева, а на узкой наклейке над текстом), слева, справа, над
  текстом, под текстом. Заданную сторону раскладка выполняет буквально, но если рядом с кодом
  текстовой колонке не остаётся ширины, она переставляет текст под код и **пишет об этом** — молча
  переигрывать выбор человека нельзя;
- **вид кода** — скруглённый, точками или классическая матрица. На считывание форма клетки не влияет
  (сканер берёт пробу в середине клетки, проверено настоящим декодером во всех трёх видах), но у
  «точек» соседние клетки не смыкаются, и на мелкой клетке они теряют по краю печатную точку — об
  этом предупреждает раскладка. У классического кода нет окошка с подписью в центре;
- **подпись назначения** («Инструкция для заказчика») — «сам» (первой строкой в колонке текста, у
  кода ничего не отнимает) либо полосой во всю ширину сверху или снизу, с выравниванием по центру,
  левому или правому краю. Полоса читается заметнее, но забирает высоту у кода — это видно на
  предпросмотре сразу;
- **подпись в окошке по центру кода** — до 15 знаков, и длиннее четырёх она верстается в две-три
  строки (`QrHoleText`). Плашке расти некуда: её сторона — 20 % стороны кода, больше нельзя, это
  предел того, что вытягивает коррекция ошибок. Поэтому «ИНСТРУКЦИЯ» одной строкой упиралась в
  ширину и вырождалась в нечитаемый кегль, а разложенная в три строки занимает квадрат вместо
  полоски и печатается заметно крупнее. Если и этого не хватает, окно говорит, каким кеглем подпись
  напечатается на самом деле.

Сама наклейка верстается визуалом WPF под размер из
настроек — миллиметры переводятся как `мм × 96 / 25.4`. Печатается **без диалога выбора принтера**,
на принтер этикеток из настроек; неизвестное имя принтера не роняет печать, а тихо падает на принтер
Windows по умолчанию, о чём сообщается в статус-строке. Рядом — «Пробная печать» тем же кодом и того
же размера.

Что синхронизируется, а что нет: адрес, размер этикетки и папка наклеек — **общие** (политика
предприятия, задаётся один раз и доезжает до всех), а **имя принтера — per-machine**
(`ConfigSyncService.SkipSettingsKeys`): у соседа принтер называется иначе, и чужое имя молча увело бы
печать в никуда.

**Наклейки** — кнопка в сайдбаре (раздел «Дополнительно») и «Открыть наклейки» на вкладке «Печать».
Это папка с готовыми шаблонами на печать («Проверено ОТК», «Внимание! Проверьте перед подключением»
и т.п.), а не ещё один справочник: ни таблицы в базе, ни синхронизации, ни модерации — окно со
списком файлов, печать (ассоциацией файла, как у PDF инструкции), **загрузить шаблон**, открыть,
открыть папку. Список перечитывается при каждом возврате в окно, поэтому кнопки «Обновить» нет, а
колонки «Изменён» — потому что дату шаблона наклейки никто не спрашивал. Вложенные папки показываются
колонкой «Раздел»; загрузка кладёт файл в подпапку выделенной строки, чтобы разложенные по темам
шаблоны не приходилось перетаскивать руками.

Отдельной синхронизации у наклеек нет и не нужно: папка лежит на общем диске, и положенный файл
видят все сразу. Нужно другое — **чтобы у всех сходился путь к ней**, и вот тут была дыра. По
умолчанию папка `<диск>\Конфиг\Наклейки`, настраивать нечего; но стоило администратору выбрать
другую обзором, в настройку уезжало `Z:\…` с буквой ЕГО машины, а сама настройка синхронизируется —
у коллеги с той же шарой под `Y:` наклейки пропадали. Теперь обзор сохраняет **хвост от корня
диска** (`SharedFolderPath.ToPortable`), а уже уехавшее абсолютное значение спасается на чтении:
записанной папки нет — ищем такую же под своим корнем, отбрасывая ведущие сегменты по одному
(`SharedFolderPath.Resolve`). Не нашли — путь остаётся как записан: «папка недоступна» честнее
молчаливой подмены. То же правило и у папки бланков паспортов — она общая ровно так же.

### Перестроить структуру диска

Разовая операция (Настройки → Иерархия → «Перестроить структуру диска…»), которой не хватало после
смены правил раскладки: новые правила действовали только для НОВЫХ загрузок, а всё, что копилось на
диске годами, оставалось как было.

Что делает (каждый пункт включается отдельно):

- **имя файла прошивки = имя папки версии** (`FirmwareNaming.BuildFirmwareFilename` теперь строит имя
  от полной строки версии, без отдельной даты через подчёркивание и без `ToUpperInvariant`);
- **инструкции — на третий диск**, если он настроен, с копией рядом с прошивкой на первом по желанию
  и с копией на хостинге, если он настроен;
- **пять папок внутрь версии** (этап 4): файлы прошивки собираются в подпапку `Прошивка`, рядом с ней
  заводятся `Инструкция`, `Карта Modbus`, `Карта ВВ`, `HMI`. Имя самой папки версии **не меняется**,
  поэтому `disk_path` остаётся валидным у всех коллег, включая не обновившихся. `CHANGELOG.md`
  остаётся в корне папки версии — его читают по фиксированному пути;
- **ОПЦ внутрь контроллера** (этап 5): `ПО\<тип>\<подтип>\ОПЦ\<версия>` →
  `ПО\<тип>\<подтип>\<контроллер>\ОПЦ\<заявка>_SN<номер>`. Единственная операция всей перестройки,
  которая **меняет** `disk_path`; `CHANGELOG.md` с номером версии дописывается **до** переименования
  (иначе номер восстановить неоткуда), а у коллег путь чинится не синхронизацией, а кнопкой
  **«Найти переехавшие ОПЦ»** на своей машине (`HierarchyService.RepairOpcDiskPaths` — ищет папку с тем
  же номером версии, ничего не двигает и не удаляет; не нашёл — путь не трогает).

После первой удавшейся перестройки включается настройка `disk_layout_v2`, и она уезжает
синхронизацией всем: с этого момента **новая** версия сразу заводится с пятью своими папками, файл
прошивки ложится в `Прошивка`, а карты/инструкция/HMI — в свои папки внутри версии. До перестройки
всё как раньше — иначе одна обновлённая машина раскладывала бы версии по-новому на диске, где все
остальные лежат по-старому.

**Читаются обе раскладки всегда**, независимо от флага и порядка обновления машин (`VersionLayout`):
файл прошивки ищется и в `Прошивка`, и в корне папки версии; документ — сначала в своей папке версии
(если в ней есть файлы), потом в общей папке контроллера. Поэтому пустая папка `Инструкция` внутри
версии ничего не прячет, а общий документ контроллера по-прежнему виден всем её версиям — копий
документов перестройка не делает, чтобы «карту обновляют в одном месте» осталось правдой.

Три свойства, без которых такую операцию нельзя выпускать, и они есть: **сухой прогон** (сначала
«Показать план», он ничего не меняет), **журнал** (`Конфиг\migration_log_<дата>.json`, пишется ДО
первой операции и переписывается после) и **идемпотентность** (повторный прогон видит уже сделанное;
прерванный дочищается следующим).

Чего операция сознательно НЕ делает и почему:

- **не переименовывает файл в многофайловой папке версии.** Имя файла хранится в
  `fw_versions.executable_hint`, а он при импорте общего конфига у совпавших строк не обновляется —
  переименовав файл там, где имя и есть носитель подсказки «чем открывать», мы сломали бы коллегам
  «Открыть прошивку ПЛК»;
- **не переименовывает папки обычных версий** — имя папки версии остаётся якорем, на котором держится
  вся синхронизация (`disk_path` у совпавшей записи импортом конфига не обновляется никогда). Меняется
  оно ровно у ОПЦ, и только потому, что там оно и было носителем неверной информации;
- **не копирует документы контроллера в каждую версию.** Это удвоило бы диск и убило бы смысл «карту
  обновляют в одном месте, и она обновилась у всех версий». Внутрь версии попадают только те
  документы, которые приложат именно к ней после переезда.

Переименование доводится до базы: правятся `filename` и `executable_hint` у **всех** записей этой
папки, включая те, у которых `disk_path` уже устарел (папку переименовали на диске, и найдена она
соседом по метке сборки).

### Осмотр

Приём фото/сканов с телефона (по QR-коду, см. ниже) и файловый менеджер папки осмотра с
предпросмотром. Предпросмотр изображения автоматически масштабируется под размер панели (вписан
пропорционально, `Viewbox`) и поддерживает минимальное редактирование: поворот на 90°/270°
(`⟲`/`⟳`, без потери качества — каждый поворот считается заново от исходного файла, а не от уже
повёрнутой картинки), с сохранением либо поверх исходного файла (с подтверждением — папка осмотра
рабочая, не архивная), либо отдельной копией. Обрезка (crop) не реализована — сознательно оставлено
за рамками минимального набора правок.

Рядом с QR-кодом — заметное напоминание, что телефон должен быть в той же Wi-Fi/локальной сети, что
и этот компьютер (иначе ссылка из QR не откроется), и кнопка «Как подключить папку с телефона» с
пошаговой инструкцией (Android/iOS) для постоянного подключения папки осмотра как сетевой папки
(SMB) через файловый менеджер телефона — в отличие от QR-загрузки (которая всё равно требует каждый
раз открыть ссылку и нажать «Отправить»), после такого подключения любое фото, сохранённое в эту
папку с телефона, сразу считается «залитым», без отдельного шага. Инструкция пытается сама
определить и показать реальный сетевой (`\\сервер\...`) адрес папки осмотра, если она лежит на
подключённом сетевом диске.

Ссылка в QR-коде содержит **одноразовый токен** (случайные 16 байт в пути) — генерируется заново
при каждом открытии страницы/поднятии сервера, старая ссылка после этого недействительна, угадать
или переиспользовать её нельзя. **Автоочистка** папки осмотра по возрасту файлов (настраивается тут
же, на странице «Осмотр» — 0 означает «не чистить») подчищает старые сканы/фото сама, чтобы папка не
копилась бесконечно.

### Тикеты

Баг-репорты и предложения по самой программе — отдельная страница в сайдбаре, видна всем ролям, но
с разным набором действий:

- **Наладчик / Программист** — создают тикеты (тип: баг/предложение/другое + текст) и видят только
  **свои** — привязка идёт по имени пользователя Windows (`Environment.UserName`), так как роли в
  приложении общие/парольные, а не персональные учётки.
- **Администратор** — видит тикеты всех пользователей со всех машин и может менять статус (Открыт →
  В работе → Закрыт, либо переоткрыть).

Хранение — локальная таблица `tickets` в `po_finder.db` на каждой машине, синхронизация между
компьютерами — отдельный от общего конфига (`ConfigSyncService`) канал: каждое действие (создание
тикета, смена статуса) сразу пишется отдельным JSON-файлом-событием в
`{диск}\Конфиг\tickets\` (maildir-подобный append-only лог, см. `TicketSyncService`), а не как часть
единого снимка `po_finder_config.json`. Так несколько человек, создающих тикеты с разных машин
одновременно, никогда не затирают тикеты друг друга — в отличие от целиком перезаписываемого
снимка конфига, где это было бы гонкой. Каждая машина независимо подтягивает ещё не увиденные файлы
при каждом открытии страницы «Тикеты»; смена статуса разрешается по принципу «побеждает более
новое событие» (по временной метке), так что применение событий в любом порядке или на нескольких
машинах сходится к одному и тому же результату. События, которые не удалось записать на диск сразу
(сеть недоступна), остаются в локальной очереди (`ticket_outbox`) и досылаются при следующем
открытии страницы. Если при открытии страницы что-то не удалось отправить/принять, это больше не
тихая ошибка — статус-бар/история уведомлений сообщают «Синхронизация тикетов: не удалось обработать
файлов: N», а при следующем успешном открытии — «Синхронизация тикетов восстановлена» (уведомление
показывается один раз на переход в проблемное/нормальное состояние, а не на каждое открытие
страницы, пока диск недоступен).

**Выгрузка тикетов** (кнопка «Выгрузить…») складывает тикеты в один zip, который можно унести с
рабочей машины: флешкой, почтой, через страницу приёма. Нужно это затем, что весь описанный выше
обмен живёт на сетевом диске конторы, а тот, кто эти тикеты чинит, до диска не достаёт — до кнопки
текст приходилось пересказывать своими словами, а скриншоты пересобирать руками.

Окно отбора спрашивает, что выгружать (только открытые и в работе / всё, что видно на странице /
один выделенный тикет) и прикладывать ли файлы из тикетов. Вложения лежат на сетевом диске, поэтому
без него галочка гаснет, а тексты выгружаются как обычно — они в локальной базе. В архиве:
`tickets.md` (читать человеку, с полным текстом, а не обрезанным, как в таблице), `tickets.json` (то
же самое для разбора программой) и `attachments/{id тикета}/…`. Архив пишется через временное имя:
оборвавшаяся на середине выгрузка не оставит под нужным именем битый файл, который потом уедет
почтой как настоящий. Вложение, которое не удалось прочитать, не срывает выгрузку, но и не пропадает
молча — про него написано в итоговом сообщении. Реализация: `Core/Services/TicketExportService.cs`.

### Сетевые диски

Отдельная страница (не вкладка Настроек — доступна всем ролям, так как каждый настраивает свой
компьютер сам, и эти пути принципиально локальны):

- **Путь к диску** (WebDAV / сетевая папка) — корень, под которым живут `ПО/`, `Параметры/` и
  служебная папка `Конфиг/` (справочник, теги, резервы номеров, тикеты, обмен конфигом между
  машинами, маркер ревизии).
- **Второй диск** — шкафы/электросхемы, используется страницей Поиска в режиме «Схемы» (см. выше).
- **Третий диск (инструкции)** — необязательный отдельный диск только под инструкции: они самые
  тяжёлые и нужны в том числе с телефона. Раскладка на нём **зеркальна первому диску** и нигде не
  хранится — путь считается заменой корня (`InstructionDiskResolver`), поэтому переименование
  подтипа/контроллера на первом диске действует и на третьем, а неверно настроенный корень не может
  увести файл в чужую папку. В базу при этом пишется путь **на первом диске**: буква третьего у
  каждой машины своя, и записанная в общий конфиг она сломала бы карточку у всех (`InstructionStorage`).
  На первом диске рядом с прошивкой остаётся **настоящая копия документа** (галочка рядом), а не
  ярлык на него: ярлык мёртв на машине, где третий диск не подключён, мёртв на флешке и бессмыслен
  на хостинге, а путь, записанный в базу, при нём указывал на несуществующий файл. Ярлыки, которые
  успели положить прежние версии программы, убираются при укладке копии. Диск не настроен или сейчас
  недоступен — инструкции ложатся на первый, как раньше.
- **Копия инструкции на хостинге (S3)** — та же инструкция третьим экземпляром уходит в бакет
  хостинга, и именно она открывается по QR-коду с наклейки с любого телефона, а не только из
  офисной сети. Раскладка в бакете повторяет раскладку диска, поэтому ссылка под QR
  (`LabelLinkBuilder`) и выложенный файл всегда указывают в одно место. Реквизиты — страница
  «Хранилище», раздел «Реквизиты»; ключи доступа не вписываются руками, а перетаскиваются
  файлом, каким его прислал хостинг (зона перетаскивания; разбор терпим к формату — txt, csv, json,
  env, письмо с подписями, две голые строки, см. `S3SecretsFile`). Пока файл с ключами не загружен,
  выкладки просто не происходит и всё работает как прежде (`S3Settings`, `InstructionPublisher`,
  `S3Client`).
- **Папка осмотра** — куда попадают сканы/фото по QR и файлы, накопленные во время осмотра;
  автоочистка по возрасту настраивается прямо на странице «Осмотр» (см. ниже).

**Получение изменений справочника — по факту изменения файла, не по таймеру.** Каждый экспорт
общего конфига поднимает счётчик в маленьком незашифрованном файле-маркере `Конфиг\revision.json`
(вместе с человекочитаемым журналом последних изменений). Другие машины подхватывают новую ревизию
сами, без подтверждения — тремя путями сразу: `FileSystemWatcher` на этот маркер (почти мгновенно,
best-effort — не каждая сетевая шара рассылает уведомления об изменении файлов), короткий фоновый
опрос самого маркера (~75 секунд — сам конфиг читается и разбирается только если ревизия
действительно выросла, а не на каждый тик) и кнопка «Синхронизировать сейчас» вручную как
подстраховка. Настраиваемого интервала получения в интерфейсе больше нет — прежний интервал
разряженно опрашивал ровно тот же дешёвый маркер, не давая ничего по сравнению с частой проверкой
самого маркера.

**Изменения общего справочника отправляются сразу**, не дожидаясь интервала. Тип и подтип шкафа,
контроллер, модификация, производитель ПЧ/УПП, расширения файлов (оба списка), тег, резерв номера —
после любой такой правки приложение само делает «сначала забрать чужое, потом отдать своё»
(`PushCatalogChange`). Отправка по-прежнему разрешена только администратору. Отдельный интервал
(«Отправка изменений на диск», по умолчанию выключен) — не основной механизм, а подстраховка на
случай, если немедленная отправка не удалась (диск был недоступен в момент правки): периодически
досылает накопленное повторно; кнопка «Отправить сейчас» работает и без него.

**Видимость с обеих сторон.** На принимающей машине поступившие изменения видны сразу баннером
«Поступили изменения с общего диска (N): …» (короткое описание — до 5 записей из журнала маркера,
дальше «и ещё N») и отдельной записью в истории уведомлений — баннер прячется сам через несколько
секунд, уведомление остаётся. На отправляющей машине, пока изменения ещё не улетели (диск был
недоступен), в статус-баре видна плашка с их числом.

**Конфликты** — одна и та же запись независимо изменена на двух машинах с последнего согласованного
состояния — не применяются автоматически: видны отдельной плашкой («Показать и решить») и решаются
в диалоге, где по каждому расходящемуся полю можно выбрать свою версию или чужую.

**Эталонная синхронизация** (только администратор) — кнопка «Сделать это состояние эталонным для
всех» на отдельной карточке с предупреждающей рамкой: справочник этой машины (типы шкафов, подтипы,
контроллеры, модификации, производители, теги, оба списка разрешённых расширений) становится
образцом для всех остальных машин — того, чего здесь нет, не будет и у них (прошивки и файлы
параметров не затрагиваются). Перед отправкой — предпросмотр разницы (что добавится, что удалится
у получателей) относительно того, что сейчас лежит в общем конфиге на диске. Опасная, редкая
операция, поэтому подтверждается отдельным диалогом.

### Хранилище

Отдельная страница (администратор и программист) про то, что уходит на хостинг. До неё выкладка
была побочным действием загрузки версии: получилось — хорошо, нет — строчка в предупреждениях,
которую никто не читал, и узнать постфактум, лежит документ на хостинге или нет, было неоткуда.

Разделы страницы переключаются той же полосой кнопок, что и вкладки «Настроек». Стандартный
`TabControl`, стоявший здесь сначала, был единственным на всё приложение и рисовался системной темой
Windows — светло-серые ярлычки с рамкой, ни одного цвета из палитры: в тёмной теме белёсая полоса
поверх тёмного фона, в светлой — чужой по виду блок, не похожий на остальные страницы.

**Состояние** — список того, что должно лежать на хостинге: версия, что за документ, размер, адрес
и ключ объекта. Список строится по базе и диску, без обращения к сети, поэтому страница
открывается мгновенно. «Проверить на хостинге» спрашивает у хранилища по каждой строке, есть ли
объект, — это ответ хранилища, а не наша запись о прошлой выкладке: файл могли удалить руками через
S3-клиент, выложить с другой машины, а локальную базу пересоздать. Дальше — «Выложить недостающее»,
«Выложить выбранное» и «Перезалить всё» (нужно, когда документы правили на диске, а на хостинге
осталась прошлая редакция). Долгие прогоны идут в фоне с полосой прогресса и кнопкой «Остановить»;
остановка ничего не ломает — уже выложенное остаётся выложенным. Фильтр «только те, что не на
хостинге» и контекстное меню строки: открыть ссылку, скопировать ссылку или ключ, показать файл на
диске. Там же задаётся предел размера файла и что делать с превышением — не выкладывать или
выложить с предупреждением.

**Реквизиты** — адрес хранилища, бакет, регион, папка внутри бакета, ключи доступа (файлом,
перетаскиванием) и галочка выкладки. Раньше всё это стояло на странице «Сетевые диски» рядом с
путями к сетевым папкам, к которым отношения не имеет; теперь настройка стоит там же, где видны её
последствия — что выложено, что нет и почему. На «Сетевых дисках» осталась кнопка «Открыть
«Хранилище»» с одной строкой о текущем состоянии: пришедший туда по старой памяти должен уйти на
нужную страницу, а не решить, что настройку убрали. Кнопка открывает страницу именно на
«Реквизитах», а не на том разделе, где её оставили в прошлый раз.

Здесь же — **веб-адрес диска инструкций**. Это та же самая настройка (`instruction_base_url`), что и
в Настройки → Печать, намеренно показанная в двух местах: без неё ссылке на хостинг неоткуда взяться
(это хранилище), и она же решает, что зашивать в QR на наклейке (это печать). Правка в любом из двух
мест меняет одно значение; в обоих местах об этом написано.

Адрес хранилища, бакет, регион и веб-адрес **предустановлены** рабочими значениями компании и
пустыми не бывают: стёртое поле возвращает предустановку (`ConfigService.PresetKeys`). Причина — три
разные поломки с одним симптомом «настройка не синхронизируется»: адрес, живший только умолчанием в
коде, не лежал в `settings` и потому не уезжал в общий конфиг; один раз стёртое поле глушило
предустановку навсегда; а пустая строка с машины, где адрес не настраивали, затирала его у всех
остальных. Теперь предустановка попадает в базу разовой миграцией (`Database.SeedHostingAddressesOnce`)
и дальше живёт обычной настройкой, а пустое значение по синхронизации не применяется — ровно так же,
как синхронизация не переносит удаления из справочников.

**Журнал** — что происходило при последних прогонах, целиком, с причинами отказов и кнопкой
проверки доступа к хранилищу текущими ключами.

**Написание в адресах** — справочник транслита. Диск целиком русский, а раскладка бакета повторяет
раскладку диска, поэтому и ключ объекта, и ссылка под QR получались кириллическими: формально это
законный адрес, но по дороге к телефону его перекодирует кто угодно — почта, мессенджер,
S3-клиент, — а подпись запроса считается по точной байтовой форме ключа. Перевод считается
автоматически («ПЖ» → `PZH`, «Карта ВВ» → `Karta_VV`), а для имён с принятым английским написанием
его можно переопределить. Справочник общий и синхронизируется: ссылку печатает одна машина, а файл
выкладывает другая, и перевод у них обязан совпадать.

Признак «на хостинге есть / не найден» и кнопка проверки есть и в окне «QR и этикетка» — наклейку
клеят на шкаф, и если файла там нет, узнать об этом надо до печати.

### Чистка диска

Страница только для администратора: она переименовывает, переносит и безвозвратно удаляет файлы на
общем диске, то есть чужую работу.

Обход находит то, что не подходит под раскладку: прошивку, названную не по имени папки версии;
документ или папку проекта не в своей папке; служебный мусор Windows. По каждой находке видно, что
не так, почему так решено и что предлагается — переименовать, перенести, удалить или оставить;
действие по строке можно поменять. «Отметить безопасные» ставит галочки только на переименование и
перенос, удаление отмечается вручную, и перед применением спрашивается подтверждение с числом
удалений. Журнал прогона пишется файлом в «Конфиг», как у перестройки структуры.

Главное свойство — не съесть нужное. Расширение из любого белого списка (ПЛК, HMI, схемы) мусором
не считается никогда, поэтому `.svg` и невыполняемые файлы ПЛК вроде KINCO и ОВЕН не пострадают.
Файл, на который ссылается запись в базе, не трогается. Внутрь папок проекта обход не заходит:
проект — единое целое. Удалять программа готова только по закрытому короткому списку служебных имён
и временных расширений, всё незнакомое показывается без предложенного действия. Прогон
идемпотентен: повторная проверка находит только то, что человек оставил.

### Настройки

Одиннадцать вкладок. Полоса вкладок в одну строку **прокручивается по горизонтали** (колесом мыши
над самой полосой): в минимальном размере окна все вкладки в строку не влезают, и без прокрутки до
крайних было не добраться вовсе.

- **Общие** — то, что реально требует прав администратора и НЕ синхронизируется по сети (путь к
  диску и настройки получения/отправки конфига переехали на страницу «Сетевые диски» выше, вход по
  AD — на вкладку «Подключение»): смена
  роли, пароли ролей (Администратор/Программист — у Наладчика пароля нет, это роль по умолчанию),
  «хранить архивы после извлечения», действие при
  закрытии окна (закрыть/свернуть в трей), запуск при входе в Windows и **запуск свёрнутым**
  (по умолчанию оба выключены — окно открывается сразу и разворачивается как обычное; «запускать
  свёрнутым» имеет смысл только вместе со свёртыванием в трей — иначе окно просто не появится и его
  негде будет открыть), «единая зона ПЛК+HMI (бета)» для «Загрузки» (см. выше — программисту и
  администратору, наладчику не показывается), путь к лоадеру (см. «Лоадер» выше), обновление самого
  приложения (см. «Обновление приложения» ниже).
- **Иерархия** — CRUD для групп/подтипов/контроллеров/модификаций/производителей параметров
  (одна строка таблицы — один подтип; тип, у которого подтипов не осталось вовсе, показывается
  строкой «(нет подтипов)» — иначе он невидим здесь, но по-прежнему предлагается в «Загрузке ПО»,
  и удалить его из интерфейса нечем),
  **два независимых списка** разрешённых расширений (для основного файла прошивки ПЛК и отдельно
  для HMI-вложения), кнопки «Пересоздать структуру диска» / «Синхронизировать прошивки с диска» /
  «Сканировать неизвестные файлы» (папки на диске, не соответствующие известной иерархии — по
  каждой можно выбрать: перенести в «Неизвестное» или удалить безвозвратно), а также разовая
  операция **«Перестроить структуру диска…»** (см. ниже).
- **Прошивки** — таблица всех загруженных версий с фильтром, **двойной клик по строке открывает сам
  файл прошивки** (тем же выбором файла, что и «Открыть прошивку ПЛК» на карточке поиска: с учётом
  подсказки «чем открывать» и без подмены программы ПЛК файлом панели; модерация осталась кнопкой
  «Редактировать»), редактирование описания/тегов/типа
  пуска, **дублирование записи** (копия — это ВАРИАНТ той же прошивки: файлы не копируются, копия
  получает имя «Конфигурация N» и дальше отличается только тегами, см. «Конфигурации шкафов» в разделе
  Поиск; пачкой их удобнее заводить прямо в модерации), откат версии, **удаление версии** (безвозвратно с этого компьютера —
  помечается tombstone-удалением, а не просто стирается из базы, специально чтобы удаление
  корректно долетело и до остальных машин при следующей синхронизации конфига, а не «воскресло»
  там снова, см. `Database.TombstoneFwVersion`) прямо по выбранной строке.
- **Модерация** — версии, ещё не выведенные из модерации (см. страницу «Модерация прошивок» в
  сайдбаре — то же самое, урезанный вид для наладчика/программиста).

  **Очередь модерации одинакова на всех машинах** — как поиск и как иерархия. В очередь версия
  попадает, пока верны все четыре признака: не удалена, не архивная, не откатана, не выпущена, —
  значит и синхронизироваться обязаны все четыре, иначе «у меня чисто, у коллеги висит». Каждый едет
  вперёд и только вперёд: выпуск, откат и архивирование применяются, если входящая копия ушла дальше
  местной, но местную строку назад не тянут никогда; удаление едет **надгробием** (`deleted_at`,
  `Database.TombstoneFwVersion`), потому что отсутствие строки в снимке означает «мне её ещё не
  залили», а не «удалена». Опознаётся строка по переносимому `fw_versions.sync_id` (с откатом на
  прежний ключ подтип+контроллер+`version_raw`): одного натурального ключа не хватало — его ломают
  правки, которые сама же программа и разрешает (переназначение контроллера, переписывание hw меняет
  `version_raw`), и после них решение модерации было не к чему применить, у коллеги вставлялся
  дубликат, а его исходная запись оставалась висеть в очереди навсегда. Досмотр диска тоже уважает
  надгробия (`Database.GetKnownVersionRaws`): уцелевшая на диске папка удалённой версии больше не
  заводит её заново новой записью прямо в модерацию.
- **Резервация номеров** — активные резервы номера версии (см. «Зарезервировать номер версии» в
  Загрузке).
- **Теги** — список всех тегов, встречавшихся в прошивках/параметрах, с полем-фильтром по
  подстроке в названии.
- **Быстрый доступ** — настраиваемые ярлыки быстрого запуска в сайдбаре (с иконкой,
  извлечённой из самого exe/lnk-файла).
- **Лоадер** — всё про заливку в ПЛК в одном месте: путь к Segnetics Loader (пусто — встроенная
  копия), способ подключения (USB / Ethernet / «как в Loader»), адрес ПЛК, сетевой адаптер, проверка
  связи перед заливкой и значение галочки подготовки ПЛК по умолчанию. Automation параметры
  подключения в запросе не принимает — он читает их из настроек самого Loader, поэтому выбор
  переносится туда перед каждой заливкой (`LoaderConnectionSettings`): правятся **только уже
  существующие** поля, рядом сохраняется резервная копия, при непонятном содержимом файл не трогается
  вовсе и наладчику честно предлагается выбрать режим в самом Loader. Проверка связи — TCP-проба
  порта SSH по адресу ПЛК (`PlcLinkCheck`): она не запрещает заливку, а лишь избавляет от минуты
  ожидания ради `CONNECTION_FAILED` из-за невоткнутого шнурка. Тот же выбор USB/Ethernet продублирован
  **на карточке поиска рядом с кнопкой «Загрузить в ПЛК»** — это настройка, которую меняют от шкафа к
  шкафу. Вкладка доступна всем ролям: заливает как раз наладчик, и это настройки его машины.
- **Подключение** (только администратор) — чем подтверждается вход и как ходят общие данные.
  Способ входа: домен напрямую (LDAP), веб-проверка пароля, оба, либо **корпоративный вход
  Keycloak / OpenID Connect** (см. ниже). Обмен данными: сетевая папка (как сейчас) либо сервер
  (HTTP + живые уведомления по WebSocket) — **сервера пока нет и клиент к нему не написан**, поэтому
  второй пункт сегодня только запоминает адрес: данные при любом его положении идут через папку, о
  чём переключатель прямо предупреждает. Рядом кнопки «Проверить адрес» (запрос
  `.well-known/openid-configuration`), «Проверить сервер» и «Состояние подключения» (диск, домен,
  веб-проверка, GitHub, папка обновлений одним прогоном).
- **Печать** (видна всем ролям) — всё, что уходит на принтер: веб-адрес диска инструкций и размер
  этикетки с QR, принтер этикеток, пробная печать и папка с шаблонами наклеек (см. «Этикетка с QR и
  наклейки» ниже). Общие настройки (адрес, размер, папка) правит только администратор — они уезжают
  на все машины с конфигом; выбор принтера и сама печать доступны всем, печатает как раз наладчик.
- **Пользователи** — собственный ростер приложения (AD-логин, роль, первый/последний вход) для
  всех, кто хоть раз вошёл по AD-логину/паролю и не попал в одну из настроенных AD-групп ролей
  (см. ниже), с фильтром по логину/роли; администратор может сменить роль записи в ростере вручную.

#### Роли и доступ

| Роль | Поиск | Осмотр | Модерация прошивок | Загрузка | Параметры | Паспорта | Настройки* | Сетевые диски | Тикеты |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| Наладчик | ✓ | ✓ | ✓ | | ✓ | ✓ | урезано | ✓ | ✓ |
| Программист | ✓ | | | ✓ | ✓ | ✓ | урезано | ✓ | ✓ |
| Администратор | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | полностью | ✓ | ✓ |

Паспорта открыты всем ролям по той же причине, что и параметры: печатает паспорт наладчик, а
заводит/правит шаблон обычно программист или администратор.

\* Наладчику/программисту в Настройках видны только вкладки «Быстрый доступ», «Лоадер» (заливает
как раз наладчик — это настройки его машины и его шнурка) и «Печать» (внутри неё — выбор принтера и
кнопки печати, общие настройки скрыты) и срок повторного входа по AD лично для
себя — смена ролей/паролей, AD-группы, способ проверки, вкладки
Иерархия/Прошивки/Модерация/Резервация/Теги/Подключение/Пользователи скрыты целиком.

Три равноправных способа сменить роль в диалоге «Сменить роль» (доступен из сайдбара):

1. **Пароль роли** — выбрать роль из списка и ввести её пароль (общий на роль, не персональная
   учётка). У Администратора пароль обязателен (на новой установке действует заводской пароль —
   его следует сменить при первом входе в Настройках → Общие; сам пароль хранится только в виде
   хэша), у Программиста — опционален (пусто в настройках = без пароля), у Наладчика пароля нет
   вообще.
2. **Вход по AD, через настроенную группу** — ввести домен/логин/пароль AD-учётки; если логин
   входит в одну из групп, указанных в Настройках → Общие → AD (по одной группе на роль), роль
   выдаётся сразу, без пароля роли. Не требует, чтобы сама Windows-сессия шла под этой учёткой.
3. **Вход по AD, без настроенной группы** — тот же домен/логин/пароль, но если группы для ролей не
   заданы (или логин ни в одну из них не входит): роль берётся из собственного ростера приложения
   (вкладка Настройки → Пользователи) — уже известный логин получает сохранённую там роль, самый
   первый вход этого логина автоматически становится «Наладчиком» (администратор может сменить
   роль в ростере вручную). Ни группы, ни ростер не требуют домена/IT-поддержки для работы — при
   их отсутствии просто ничего не ломается, доступен обычный вход паролем роли.

**Корпоративный вход (Keycloak / OpenID Connect).** Четвёртый способ, выбирается в Настройки →
Подключение и требует адреса realm и client_id от ИТ (`docs/keycloak-setup.md`). Вход идёт через
**системный браузер** (authorization code + PKCE, возврат на loopback) — пароль приложение не видит
вовсе; встроенный WebView здесь не используется намеренно, его многие провайдеры блокируют. Роль
считается по группам **из самого токена** (`RoleFromGroups`) теми же настройками
`ad_group_administrator/_programmer/_naladchik`, что и у AD — с федерацией AD в Keycloak это
буквально те же группы; группы приходят и списком, и путём (`/Antarus/Админы` — сравнивается и
последний сегмент). Ничего не совпало — роль берётся из ростера приложения, где новый человек
получает минимальную. Пока способ не выбран и не настроен, окно входа выглядит и работает как
раньше, а аварийный вход паролём администратора остаётся при любом способе.

Вся настройка AD (домен, группы, способ проверки, обязательный вход при запуске) — **локальная для
каждого компьютера**, не разъезжается по сети вместе с остальным конфигом: администратору нужно
задать её один раз на каждой машине отдельно. Опционально можно включить «Требовать вход по AD при
запуске» — тогда при каждом старте приложения (если нет ещё действующего запомненного входа на этом
компьютере, срок настраивается) появляется окно входа вместо немедленного показа главного окна;
пароль администратора остаётся аварийным способом входа, чтобы не оказаться заблокированным при
проблеме с доменом.

#### Загрузка фото с телефона

Кнопка «Фото» на странице Поиска поднимает мини-HTTP-сервер (на порту из настроек, по
умолчанию 9876) и показывает QR-код со ссылкой — телефон в той же сети открывает простую
HTML-форму загрузки и отправляет фото прямо в папку осмотра. Сервер реализован на «сыром»
`TcpListener` с самодельным разбором HTTP-запроса и multipart-тела, **намеренно не через**
`HttpListener`: у Windows `HttpListener` (HTTP.SYS) требует прав администратора или
предварительной регистрации URL (`netsh http add urlacl`) для любого адреса кроме localhost —
это сломало бы функцию для обычного пользователя без прав администратора.

#### Обновление приложения

Источник обновлений — по одному правилу везде (плашка при запуске, ручная проверка в Настройках):
если в Настройки → Общие → «Обновление приложения» указана сетевая папка — релизы ищутся в ней;
если папка пуста — используется публичный GitHub-репозиторий
([IlyaRevkin/antarus-po-finder-dotnet](https://github.com/IlyaRevkin/antarus-po-finder-dotnet)).
Источник, из которого взято обновление, всегда написан в тексте плашки/статуса, чтобы было видно,
что именно проверялось.

- **Папка**: файлы вида `AntarusPoFinder-{версия}.exe`, например `AntarusPoFinder-1.1.0.exe` — по
  одному файлу на выпущенную версию, старые версии не удаляются.
- **GitHub**: релизы репозитория (`gh release list`), версия берётся из тега (`v1.1.0` →
  `1.1.0`), файл — первый `.exe`-ассет релиза.

В обоих случаях версия сравнивается с текущей (читается из атрибутов сборки, `<Version>` в
`AntarusPoFinder.App.csproj`). Выпадающий список со всеми найденными версиями и кнопка
«Установить выбранную» позволяют поставить любую версию, в том числе более старую — это и есть
откат приложения (без переустановки вручную с чужого компьютера). Установка одинакова во всех
случаях: нужный `.exe` (локальный или скачанный с GitHub) копируется рядом с текущим, приложение
закрывается, короткий `.bat`-скрипт в `%TEMP%` дожидается завершения процесса, подменяет `.exe`
на выбранную версию и перезапускает приложение.

При запуске приложение само проверяет обновления (через ~2.5 с) и повторяет проверку раз в
30 минут, пока открыто. Галочка «Устанавливать найденные обновления автоматически при запуске»
в тех же настройках **включена по умолчанию** — найденная версия ставится без подтверждения.
Если её снять, вместо установки показывается плашка сверху окна с кнопкой «Установить» (она
единственная не прячется сама — иначе вместе с текстом ушёл бы единственный способ начать
установку).

Дефолт был выключенным до 1.30.0, и это оказалось настоящей причиной жалоб вида «фикс не
работает»: транспорт обновления исправен целиком (релиз виден, `.sha256` сходится, установка
проходит), но единственной дорогой к новой версии оставалась плашка, а наладчик в Настройки не
заходит и плашку пропускает — и неделями смотрит на давно исправленные баги. Смена дефолта
действует только на установки, где галочку ни разу не трогали: явно сохранённое «выключено»
не перебивается.

Сломавшаяся проверка обновлений (GitHub недоступен из заводской сети, прокси режет TLS, сетевая
папка отвалилась) больше не проходит бесследно — раньше исключение молча гасилось, и приложение
оставалось на старой версии сколько угодно долго без единого следа. Теперь об этом приходит
уведомление, один раз на переходе в «не работает», а не на каждой проверке раз в 30 минут.

Найденная новая версия попадает в историю уведомлений **всегда**, даже если категория «Обновления
приложения» выключена: галочка категории глушит всплывающую плашку — это её работа, — но не должна
делать существование новой версии ненаблюдаемым (историю пользователь открывает сам, когда идёт
разбираться, почему у него старые баги). Раньше выключенная категория вместе с выключенным
автообновлением означала, что релиз молча выбрасывался. Записи дедуплицируются по версии — иначе
проверка раз в 30 минут сыпала бы по строке за полчаса до самой установки.

**Что нового сохраняется.** После обновления окно «Что нового» показывается разово, но его текст
больше не пропадает: он **сохраняется** и в историю уведомлений (строкой с кнопкой «Показать»,
открывающей то же окно), и в постоянный журнал изменений. Журнал открывается кнопкой **«История
изменений программы»** в Настройки → Общие → «Обновление приложения» (`AppChangelogWindow`): слева
список версий, которые эта установка видела (новые сверху, с датой появления обновления здесь),
справа — что менялось в каждой. Журнал per-machine (это история обновлений именно этого компьютера,
не общий справочник — в синхронизацию между ПК не уходит), хранит до 50 последних версий.

Вся цепочка самообновления проверена живьём (изолированный профиль, реальный GitHub): установленная
1.29.0 с включённой галочкой сама скачала ассет релиза 1.30.0 (179 МБ, ~15 с), сверила размер и
SHA256, подменила собственный `.exe` и перезапустилась уже как 1.30.0 — без единого клика.
Самообновление безопасно и для установки из MSI: ярлыки в `installer/Package.wxs` не
advertised (`AllowAdvertise="no"`, прямой `Target=`), поэтому запуск по ярлыку не запускает
самовосстановление MSI, которое иначе вернуло бы на место старый `.exe`.

Чтобы выпустить новую версию:

1. Поднять `<Version>` в `AntarusPoFinder.App.csproj`.
2. `installer/build.ps1` (без `-Version` — читает его из csproj, см. шаг 1) публикует портативный
   self-contained `.exe` и собирает вокруг него MSI-инсталлятор (см. `installer/Package.wxs`) одной
   командой:
   ```powershell
   powershell -File installer/build.ps1
   ```
   Результат — `installer/AntarusPoFinder-{версия}.exe` (портативный, без установки) и
   `installer/AntarusPoFinder-{версия}-setup.msi` (устанавливает в `%LocalAppData%`, добавляет
   ярлыки, поддерживает апгрейд/переустановку той же или более новой версии).
3. Переименовать/скопировать exe в формат `AntarusPoFinder-{версия}.exe` (уже в этом виде из шага 2)
   и либо положить оба файла в папку обновлений на сетевом диске рядом с предыдущими версиями, либо
   опубликовать GitHub-релиз с **обоими** файлами:
   `gh release create v{версия} AntarusPoFinder-{версия}.exe AntarusPoFinder-{версия}-setup.msi`.
   Приложение само проверяет обновления только через `.exe`-ассет (портативная подмена файла, см.
   выше) — MSI в релизе нужен для тех, кто ставит/переустанавливает приложение впервые или через
   инсталлятор, а не через самообновление.

## Безопасность

- **Пароли ролей** (Администратор/Программист) хранятся не открытым текстом, а хешем (PBKDF2/
  SHA256, случайная соль на каждый пароль, 100 000 итераций); сравнение при входе — с постоянным
  временем выполнения, чтобы не открывать канал для подбора по времени ответа.
- **Общий конфиг на сетевом диске** (`Конфиг\po_finder_config.json`) шифруется (AES-GCM) —
  открывать его текстовым редактором и на глаз править JSON больше нельзя; это защита от «зашёл и
  поправил», не от обратной разработки самого приложения (ключ выводится из фразы, зашитой в код, —
  как у любого клиентского секрета, его можно вытащить, декомпилировав exe). Расшифровка
  одновременно проверяет подлинность содержимого: подменённый или повреждённый на общем диске файл
  не расшифруется молча в мусор, а будет отклонён.
- **Целостность автообновлений** — у скачанного с GitHub или взятого из сетевой папки обновлений
  `.exe`-файла проверяется размер (ловит обрыв/усечение скачивания) и, если у релиза есть
  сопутствующий `.sha256`-файл (кладёт `installer/build.ps1`, см. «Обновление приложения» выше), —
  SHA256-хеш (ловит подмену/повреждение файла); установка отменяется, если проверка не прошла.

## Сборка и запуск

Требуется .NET 8 SDK.

```bash
dotnet build                 # долг / debug-сборка всего решения
dotnet test                  # смоук-тесты Core
dotnet run --project AntarusPoFinder.App   # запуск из исходников
```

Портативный релизный `.exe` (не требует установленного .NET на целевой машине, весь рантайм
внутри, ~160 МБ):

```bash
dotnet publish AntarusPoFinder.App/AntarusPoFinder.App.csproj -c Release -r win-x64 \
  --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true \
  -o publish
```

Результат — `publish/AntarusPoFinder.App.exe`. Для полноценного релиза (portable exe + MSI разом,
версия берётся из csproj) используйте `installer/build.ps1` — см. «Обновление приложения» выше.

База данных создаётся автоматически при первом запуске в
`%LocalAppData%\AntarusPOFinder\po_finder.db`.

## Отличия и известные ограничения

По сравнению с предшествующим прототипом на Python сознательно **не портированы**:

- **Автодополнение названий шкафов по второму диску** — второй диск (электросхемы) сегодня
  используется для поиска и просмотра файлов схем (см. «Поиск» → режим «Схемы»), но не для
  подсказок/автодополнения имени шкафа в других полях формы, как это было в прототипе.
- **Легаси-система «Правила»/«Шаблоны»** — более старый способ привязки прошивок к именам
  шкафов без иерархии; полностью заменён иерархической моделью выше.
- **Прямое управление сканером через WIA** — кнопка «Сканировать» использует только упрощённый
  путь (запуск системного приложения «Сканер Windows» + сравнение содержимого папок до/после
  + ручной выбор файла как запасной вариант).

Реализовано как экспериментальная настройка:

- **«Единая зона ПЛК+HMI»** — помечена в самом интерфейсе как бета: определение по расширению файла
  может ошибиться на нестандартной структуре проекта.

Не реализовано (осознанный бэклог, часть уже подготовлена схемой БД):

- **Уведомления по почте о новых версиях прошивки** — таблица `users`/поле `author_id` у каждой
  версии уже фиксируют, кто и когда загрузил, но рассылки нет.
- **Персональные учётные записи вместо общих ролевых паролей** — вход по AD-логину/паролю
  (см. «Роли и доступ» выше) уже проверяет конкретного человека и запоминает его в собственном
  ростере приложения (Настройки → Пользователи), но результатом всё равно остаётся одна из трёх
  общих ролей (наладчик/программист/администратор), не персональные права по каждому пользователю
  отдельно — вход паролем роли (без AD вовсе) как способ входа никуда не делся и работает
  параллельно.

  Services/        — ConfigService, HierarchyService, SearchService, SchematicService, PslInspector,
                     FirmwareUploadService, FirmwareAttachmentsService, ParamFileLinkService,
