# План перестройки иерархии, файлов версии, инструкций и QR

Базис: `origin/master @ 604b12d`. Все пути — от корня репозитория.

---

## 0. Главный вывод

Из семи требований **пять можно сделать без переезда данных на диске** (имя файла = имя версии,
заглушка-PDF, QR + этикетка + печать, учёт версий файлов, «унаследовано от версии X» для всех типов
файлов) — они трогают только код и БД. **Переезда данных требуют два**: перенос пяти папок
(`Инструкция / Карта Modbus / Карта ВВ / HMI / Прошивка`) с уровня контроллера **внутрь папки
версии**, и перенос «ОПЦ» с уровня подтипа **внутрь контроллера** с переименованием папок в номер
заявки/SN. Именно эти два несут весь риск рассинхрона с коллегами.

Хорошая новость: **при переносе пяти папок внутрь версии сама папка версии не переименовывается и
не переезжает** — значит `fw_versions.disk_path` не меняется, и рассинхрона путей между машинами не
возникает вовсе. Плохая новость: у **ОПЦ** путь меняется, а `disk_path` при импорте конфига на уже
совпавшей записи **не обновляется** (`Database.ConfigExchange.cs:1169-1188` — его нет в `SET`),
поэтому у коллег ОПЦ-прошивки после переезда молча станут «⚠ на диске не найдена». Чинится
отдельным локальным проходом, а не синхрой.

## 1. Как устроено сейчас

### 1.1. Иерархия папок

Построение путей — одно место: `AntarusPoFinder.Core/Services/HierarchyService.cs:78-115`.

```

IoMapPath(...)     → PoCtrlFolder + "\Карта ВВ"        (:100)
ModbusMapPath(...) → PoCtrlFolder + "\Карта Modbus"    (:103)
HmiPath(...)       → PoCtrlFolder + "\HMI"             (:106)
```

Имена спецпапок — `HierarchyDefaults.cs:6-15`. Папки `Прошивки` **нет вообще** — файл прошивки
лежит прямо в папке версии.

### 1.2. `disk_path` и локализация путей

`fw_versions.disk_path` хранится **абсолютным**, с корнем машины-загрузчика (`Database.cs:85`).
Корень (`root_path`) — **per-machine, не синхронизируется** (`ConfigSyncService.cs:104`). Чужой путь
приводится к своему через `FirmwarePathLocalizer.Localize` (якорь — первый сегмент `ПО`/`Параметры`,
`:41-56`), вызывается в 8 местах.

Ключевое свойство для миграции: **пока хвост от `ПО\` неизменен, чужой `disk_path` продолжает
работать на любой машине.** Всё, что не меняет хвост, — бесплатно для синхронизации.

### 1.8. Синхронизация — что нельзя сломать

- **Единица обмена** — один зашифрованный JSON на общем диске (`Конфиг\po_finder_config.json`,
  `ConfigSyncService.ConfigPathFor:157`) + незашифрованный маркер `Конфиг\revision.json`.
- **Общий конфиг перезаписывается ЦЕЛИКОМ** каждой отправкой (`Database.ConfigExchange.cs:175-177`).
  Отправлять может только администратор.
- **`schema_version` = 1** (`ConfigSyncService.cs:73`). Расхождение **не блокирует** приём —
  применяется принудительно с уведомлением (`ConfigUpdateInfo.CriticalSchemaMismatch`).
- **Совместимость «новые поля ↔ старый клиент» уже безопасна:** `IsSetting` (`:92-93`) пропускает
  только `JsonValue`, поэтому **любой новый массив/объект в корне конфига старый клиент молча
  игнорирует**; `System.Text.Json` игнорирует неизвестные свойства.
- **Опасность ровно одна:** старый клиент-администратор, отправив свой снимок, **сотрёт с диска все
  новые секции** — конфиг перезаписывается целиком. Это и есть исторический сценарий «синхра
  сломалась на рассинхроне версий».
- **Ключ сопоставления прошивки** — `(subtype_id, controller_id, version_raw)`
  (`ConfigExchange.cs:1052-1063`). Пути в ключ не входят: переезд не плодит дубликаты, но
  `disk_path` у совпавшей записи **никогда не обновляется** (`UPDATE` на :1169-1188).
- `CHANGELOG.md` — второй, дисковый канал доставки описания/типов пуска/тегов (`ChangelogFile.cs`).
  **Расширять его новыми строками нельзя:** парсер `TryRead:66-107` считает любую неизвестную строку
  шапки началом ТЕЛА, то есть новый заголовок попадёт в описание версии.
- Есть работающий приём «операция-переименование едет отдельным журналом» — `hw_rewrite_log` +
  `ConfigSyncService.ReplayHwRewrites` + watermark `hw_rewrite_applied_at`. **Готовый шаблон для
  миграционных операций** (`Database.HwRewriteLog.cs`, `HierarchyService.ReplayControllerHwRewrite:224`).

## 2. Целевая архитектура

### 2.1. Раскладка на диске

```
<диск 1 — основной>
  ПО\<тип>\<подтип>\<контроллер>\<версия>\          ← имя папки НЕ меняется
        Прошивка\        <версия>.psl | файлы проекта Кинко/Овен
        Инструкция\      <версия>.pdf | <версия>.pdf.lnk → диск 3 | пусто
        Карта Modbus\
        Карта ВВ\
        HMI\
        .antarus\files.json     ← реестр слотов (старые клиенты его не видят)
        CHANGELOG.md            ← формат не трогаем

  ПО\<тип>\<подтип>\<контроллер>\ОПЦ\<заявка|SN>\   ← та же пятёрка внутри

<диск 3 — инструкции>
  ПО\<тип>\<подтип>\<контроллер>\<версия>\<версия>.pdf   ← одна папка вместо пяти
```

Три решения, которые надо принять осознанно:

1. **Имя файла инструкции фиксировано** — `<версия>.pdf`, всегда, и для заглушки, и для готового
   документа. Единственный способ выполнить «путь не меняется, меняется только файл» и сохранить QR
   валидным. Исходник `docx` — рядом под тем же именем.
2. **Приложение НИКОГДА не ходит через `.lnk`.** Ярлык на первом диске — для человека в проводнике.
   Программа считает путь на третьем диске сама, зеркальным правилом. Иначе
   `DocFileResolver.LatestFileIn` подберёт `.lnk` как «самый свежий файл», `HasInstructions` станет
   true, а `DocxToPdfConverter` подавится ярлыком.
3. **Папка версии не переименовывается никогда** (кроме ОПЦ) — этот якорь делает миграцию бесплатной
   для синхры.

### 2.2. Новый слой: `VersionLayout`

Один статический класс в Core — единственный источник правды о том, где что лежит у версии:

```
VersionLayout.FirmwareFolder(versionDir)      → versionDir\Прошивка
VersionLayout.SlotFolder(versionDir, slot)    → versionDir\Инструкция | Карта Modbus | Карта ВВ | HMI
VersionLayout.SidecarPath(versionDir)         → versionDir\.antarus\files.json
VersionLayout.InstructionOnThirdDisk(thirdRoot, storedDiskPath, versionRaw)
VersionLayout.InstructionUrl(baseUrl, storedDiskPath, versionRaw)
```

Плюс **режим совместимости**: пока не все версии переехали, `SlotFolder` возвращает пару кандидатов
(новая папка внутри версии, старая общая папка контроллера), резолверы пробуют обе. Это позволяет
выпускать этап 4 постепенно.

### 2.3. Новая таблица `fw_version_files`

Обобщение механики «унаследовано от версии X», которая сегодня закодирована в имени папки
`{версия}_hmi` и уже породила два костыля (`DiffersOnlyInHw`, `RenameOwnHmiFolder`).

```sql
CREATE TABLE IF NOT EXISTS fw_version_files (
    fw_version_id      INTEGER NOT NULL REFERENCES fw_versions(id),
    slot               TEXT    NOT NULL,   -- instruction | modbus | iomap | hmi | firmware
    state              TEXT    NOT NULL,   -- own | inherited | stub | absent
    source_version_raw TEXT    NOT NULL DEFAULT '',  -- «от какой версии» (state=inherited)
    rel_path           TEXT    NOT NULL DEFAULT '',  -- путь ОТНОСИТЕЛЬНО папки версии
    file_revision      INTEGER NOT NULL DEFAULT 1,   -- +1 на каждую перезаливку
    content_hash       TEXT    NOT NULL DEFAULT '',  -- sha256, чтобы не гадать по mtime
    updated_at         TEXT    NOT NULL DEFAULT '',
    updated_by         TEXT    NOT NULL DEFAULT '',
    PRIMARY KEY (fw_version_id, slot)
);
```

- **`rel_path` относительный** — снимает проблему «путь коллеги ≠ мой путь» на корню, без
  `FirmwarePathLocalizer`.
- **`file_revision` + `content_hash`** закрывают требование о независимости: прошивка и инструкция
  меняются независимо, «Инструкция обновлена (ред. 3, 14.02.2026, Иванов)» — это ревизия слота, а не
  новая версия прошивки.
- **`state` + `source_version_raw`** — обобщённое «унаследовано от версии X» для всех слотов.
  Существующее HMI-поведение переводится сюда, `FirmwareCard.HmiSourceVersion:357-399` со всеми
  костылями удаляется.
- Старые колонки `io_map_path/instructions_path/modbus_map_path/hmi_path` **не удаляются** — канал
  совместимости, заполняются дублирующе (dual-write) весь переходный период.

### 2.4. Дисковый носитель реестра — `.antarus\files.json`, не `CHANGELOG.md`

`CHANGELOG.md` расширять нельзя (см. 1.8). Кладём `<версия>\.antarus\files.json`: невидим для
`ScanFwDisk.ReadFirmwareFilename` (`:847-860` перечисляет только верхний уровень), даёт состояния
слотов машине, узнавшей о версии сканированием диска, служит запасным источником при восстановлении БД.

### 2.5. Обмен реестром — отдельный файл, не общий конфиг

**Не класть `fw_version_files` в `po_finder_config.json`**: конфиг перезаписывается целиком, старый
клиент-администратор сотрёт секцию. Вместо этого — `Конфиг\file_registry\<origin>.json`, по файлу на
машину, как уже сделано с тикетами (`TicketSyncService.cs`). Слияние — по ключу
`(subtype_sync_id, controller_sync_id, version_raw, slot)` + `file_revision` как LWW.

### Этап 1 — Дешёвые победы: имя файла, заглушка, QR, этикетка, печать

**1a. Имя файла = имя версии.** В `FirmwareNaming.BuildFirmwareFilename` базой берётся
`version.Raw`, а не `NumberPart`, маркеры ОПЦ дописываются после, `ToUpperInvariant()` убирается. Для
многофайловых загрузок ничего не меняется. Плюс фоновая дочистка: для версий с ровно одним файлом в
папке — `File.Move` в каноническое имя.

⚠ **`ExecutableHint` хранит имя файла** (`Database.cs:93`). Переименовал файл — обнови
`executable_hint` в той же транзакции, иначе «Открыть прошивку ПЛК» потеряет выбранный файл. И этот
столбец **тоже не обновляется** при импорте у совпавших строк (только backfill пустого,
`ConfigExchange.cs:1128-1129`) — у коллег останется подсказка на несуществующий файл, резолвер тихо
упадёт на «первый подходящий». **Вывод: переименовывать только там, где в папке ровно один файл.**

**1b. Заглушка PDF.** `SimplePdfWriter.cs` умеет только «JPEG в PDF». Кириллица в base-14 Helvetica —
отдельная морока с кодировками; **проще рисовать текст в WPF-визуал и класть картинкой** через
существующий `WriteJpegAsPdf`. Имя — каноническое `<версия>.pdf`, чтобы реальный документ лёг на то
же место.

**1c. Веб-ссылка + QR + этикетка + печать.** Новые per-machine настройки (в `SkipSettingsKeys`, рядом
с `second_disk_path`): `instruction_base_url`, `label_width_mm` / `label_height_mm` (по умолчанию
97.5 × 72 — спор 97.5 vs 100 закрывается тем, что это настройка), `label_template` с подстановками
`{qr}`, `{url}`, `{type}`, `{subtype}`, `{controller}`, `{version}`.

URL: базовый + хвост от `ПО` + `/<версия>.pdf`. **Кириллица идёт как есть** (правка v1.65.0): в
сегменте кодируется только то, что иначе ломает разбор адреса — пробел, `%`, `#`, `?`, `\` и прочие
структурные знаки (`LabelLinkBuilder.EscapeSegment`), посегментно (целиком нельзя: «Antarus Finder» и
«Карта ВВ» дадут битую ссылку, а слеши-разделители уедут в кодировку). Прежний `Uri.EscapeDataString`
по сегменту раздувал каждую русскую букву до шести символов: на реальном пути 162 байта против 274,
то есть QR версии 11 (61 модуль) вместо версии 13 (69 модулей) — код был плотнее там, где наклейка и
так мелкая. Адрес с не-ASCII — это IRI (RFC 3987), браузеры и сканеры его принимают.
Печать — `PrintDialog.PrintVisual` по `FixedPage`; мм → DIU:
`mm * 96 / 25.4` (97.5 мм = 368.5, 72 мм = 272.1). Точка входа — пункт «QR и этикетка…» в меню «Ещё»
карточки (`FirmwareCard.AddInstructionItems:439-457`).

**Объём:** 4–6 дней. **Риск:** низкий→средний (единственный реальный — переименование файлов).

### Этап 2 — Учёт файлов версии и модерация с выбором

- Резолверы (`DocFileResolver`, `InstructionDocResolver`, `SearchView.ResolveDocFile/ResolveInstruction`)
  читают состояние из `fw_version_files`, а не гадают «самый свежий файл в общей папке».
  `absent` → пункта в меню нет; `stub` → пункт с пометкой «заглушка»; `inherited` → «от версии X».
- `EditFirmwareDialog` получает по каждому слоту радио-группу вместо текстового поля: **«Приложить
  файл…» / «Перенести с предыдущей версии (X)» / «Заглушка» / «Оставить без файла»**. Предыдущая
  версия ищется тем же запросом, что сейчас HMI (`Database.GetLatestHmiForFirmware`,
  `Database.FwVersions.cs:647`) — обобщается в `GetLatestFileForSlot(subtypeId, controllerId, slot)`.
- `FirmwareAttachmentsService.Apply` расширяется теми же исходами, пишет реестр + сайдкар +
  (dual-write) старые колонки.
- Карточка: `HmiSourceVersion` и `DiffersOnlyInHw` выкидываются, «от версии X» и «заглушка» рисуются
  по строке реестра для всех слотов одинаково. Строка «Файлы:» (`ShowFilesLine:403-433`) получает
  «инструкция ✓ (от 2.1.0042.0003)» и «карта ВВ ✓ (от …)».
- Кнопка **«Обновить инструкцию»** в карточке и в модерации: выбрать файл → положить по тому же пути
  → `file_revision + 1`, `content_hash`, `updated_at/by`. Путь и QR не меняются.
- Обмен реестром — `Конфиг\file_registry\<origin>.json`, тем же тиком, что тикеты.

**Объём:** 6–9 дней. **Риск:** средний. **Откат:** флаг «читать состояние из реестра» → выключить.

### Этап 3 — Третий диск под инструкции

- Настройка `third_disk_path` рядом с `second_disk_path`, в `SkipSettingsKeys`.
- Зеркальный путь `<третий>\ПО\<тип>\<подтип>\<контроллер>\<версия>\<версия>.pdf`.
- Загрузка инструкции идёт **на третий диск**; в `<версия>\Инструкция\` на первом кладётся `.lnk`
  (`ShortcutCreator.cs` — уже есть, через `WScript.Shell`).
- **Приложение читает третий диск напрямую, `.lnk` игнорирует.** В `DocFileResolver.LatestFileIn` и
  `InstructionDocResolver.NewestWithExt` добавляется явное исключение `.lnk`.
- Третий диск не настроен/недоступен → падаем обратно на первый.

**Объём:** 3–4 дня. **Риск:** средний. Подводные камни: `.lnk` в рекурсивных обходах; коллега со
старым клиентом увидит только ярлык и решит, что инструкции нет.

### Этап 4 — Перенос пяти папок внутрь версии ⚠ ПЕРЕЕЗД ДАННЫХ

На диске: создать `Прошивка\` и перенести туда файлы верхнего уровня кроме `CHANGELOG.md`; создать
четыре папки слотов; **не копировать** содержимое общих папок контроллера — вместо этого записать
`state=inherited, source_version_raw=<последняя версия>`; записать сайдкар.

В коде: `PlanStructure` — **папки версии в план НЕ добавлять** (иначе `версии × 5` обращений к WebDAV
каждым тиком); `FindSiblingFolder` → `VersionLayout.SlotFolder` с фолбэком; `ScanVersionFolder` —
сузить поиск `.lfs/.psl` до `Прошивка\`; `ReadFirmwareFilename` и обе ветки `ScanFwDisk` — искать в
`Прошивка\` с фолбэком; `LoaderFiles.Find`, `PlcOpenResolver`, `HmiOpenResolver` — на `VersionLayout`;
адресаты загрузки/догрузки внутрь версии; `CopyHmiProject` — папка `HMI\` без суффикса `_hmi`,
наследование из реестра.

**Почему относительно безопасно:** папка версии не переименовывается → `disk_path` остаётся валидным
на всех машинах. Старый клиент находит версию, видит файлы, может заливать. Теряет только кнопки
документации у переехавших версий. Общие папки контроллера оставляем на месте.

**Порядок выкатки:** сначала релиз, который **умеет читать обе раскладки** и никого не переносит.
Неделя на распространение. Потом включить перенос — сначала на одном контроллере.

**Объём:** 5–7 дней + мигратор 2–3 дня. **Риск:** высокий. **Откат:** журнал переносов + обратный проход.

### Этап 5 — ОПЦ внутрь контроллера ⚠ ПЕРЕЕЗД ДАННЫХ

`ПО\<тип>\<подтип>\ОПЦ\<версия>` → `ПО\<тип>\<подтип>\<контроллер>\ОПЦ\<заявка|SN>`.

- `PoCtrlFolder:80-86`, `CtrlOrOpcFolder:78` — ОПЦ перестаёт **заменять** контроллер, становится
  **дочерней**. Затрагивает `FwPath`, `ControllerFolder`, `FirmwareSubtypeLinkService.LinkExtras:167`,
  `RemoveShortcut:192`, `PruneOrphanedFirmwareShortcuts:701`.
- `PlanFwSync:747-757` — блок «вывести контроллер из hw, неоднозначный пропустить» **становится не
  нужен**: контроллер читается из пути. Чистое упрощение, заодно чинит «ОПЦ-версия не подхватилась».
- `ScanFwDisk:816-841` — `FwVersionNumber.Parse(имя папки)` для ОПЦ **перестаёт работать**. Номер
  версии придётся брать из `CHANGELOG.md` (первая строка `# <версия>`) или из сайдкара. **Мигратор
  обязан дописать CHANGELOG.md всюду, где его нет, ДО переименования** — иначе версию восстановить
  неоткуда.
- `disk_path` **меняется** → у коллег устаревает и никогда не обновляется импортом.
  `FindSiblingBuildDir` не спасёт: он ищет соседа в родителе старого пути.

**Как чинить путь у коллег:** локальный проход `RepairOpcDiskPaths` на каждой машине — перебрать свои
ОПЦ-записи с несуществующим `disk_path` и найти новое место (обход `<контроллер>\ОПЦ\*` в пределах
подтипа, сверка `version_raw` из CHANGELOG/сайдкара). Машинно-локальный, идемпотентный.

**Объём:** 4–5 дней + мигратор 2 дня. **Риск:** высокий — единственный этап, меняющий `disk_path`.

## 4. Миграция данных

### 4.1. Мигратор

Отдельная админская команда (не автозапуск) — «Настройки → Иерархия → Перевести структуру». Свойства,
без которых её нельзя выпускать:

1. **Сухой прогон обязателен** — список операций с возможностью сохранить файлом (образец:
   `Database.PreviewAuthoritativeDiff` + `AuthoritativeDiffDialog`).
2. **Журнал переносов** `Конфиг\migration_log_<ts>.json` пишется ДО первой операции, он же — вход для отката.
3. **Идемпотентность и продолжаемость** — шара отваливается регулярно; каждая папка версии
   обрабатывается независимо (принцип `RewriteHw:234-342`).
4. **Запускать на ОДНОЙ машине** — блокировка файлом-маркером `Конфиг\migration.lock` с TTL.
5. **Порядок:** дописать недостающие `CHANGELOG.md` → создать структуру → перенести файлы →
   переименовать ОПЦ → и только в конце обновить `disk_path` в БД.

### 4.2. Что делать со старыми `disk_path`

| Случай | `disk_path` | Что делать |
|---|---|---|
| Этап 4 (пять папок внутрь версии) | **не меняется** | ничего |
| Этап 5, ОПЦ | меняется | локальный `RepairOpcDiskPaths`; в синхру не отдавать |
| `io_map_path` / `instructions_path` / `modbus_map_path` / `hmi_path` | указывают на общие папки контроллера | не трогать — канал совместимости; правда в `fw_version_files.rel_path` |
| `RemapPathPrefix` (`ConfigExchange.cs:1357-1423`) | замена префикса | **не подходит**: тут меняется структура внутри, а не префикс |

### 4.3. Как не сломать машины коллег

1. **Читаем обе раскладки минимум один релиз.** Любой этап с переездом выпускается двумя релизами:
   «умеет читать новое и старое, ничего не переносит», затем (не раньше недели) «переносит».
   Автообновление включено по умолчанию (`ConfigService.cs:92`); факт распространения проверять по
   `app_users.last_login_at`.
2. **Новые данные — в отдельные файлы на шаре, не в `po_finder_config.json`.** Общий конфиг
   перезаписывается целиком, старый клиент-администратор сотрёт всё новое.
3. **`schema_version` поднять на 2** в момент, когда в конфиг реально войдёт новое. Плюс добавить в
   `revision.json` поле `min_client_version` и показывать баннер «эта шара обслуживается версией
   ≥ 1.60; ваша 1.55 — обновитесь» (маркер незашифрован, лишние поля старые клиенты игнорируют).
4. **`CHANGELOG.md` не расширять.**
5. **Общие папки контроллера не удалять до конца перехода.**

### 4.4. Что заведомо сломается у старого клиента (принять осознанно)

- Не увидит кнопки «Карта in/out / Карта modbus / Инструкция» у **новых** версий. Старые — работают.
- Не увидит инструкцию на третьем диске — увидит `.lnk`.
- Не подхватит ОПЦ-версии из новой раскладки. Дубликатов не создаст.
- Может показать «⚠ на диске не найдена» у ОПЦ после этапа 5, пока не обновится.

Ни один сценарий не приводит к порче данных или дубликатам — только к деградации отображения.

## 6. Транспорт: WebDAV / FTP / SMB / веб-сервис

Ключевой факт: **всё приложение работает с шарой как с обычной файловой системой** — `Directory.Exists`,
`EnumerateFiles`, `File.Copy`, `Directory.Move`. HTTP-клиента к диску прошивок в коде нет. Единственная
абстракция — `ISyncTransport.cs`, и она покрывает **только обмен конфигом**, не сами прошивки.

| Вариант | Как ходит приложение | Что менять в коде | Веб-ссылка для QR | Оценка |
|---|---|---|---|---|
| **WebDAV (сейчас)** | буква диска, дальше `System.IO` | **ничего** | есть из коробки | Медленный (агрессивный кэш, таймауты), но единственный, где ссылка бесплатна. Код уже написан под его тормоза |
| **SMB** | то же | **ничего** | **нет**, нужен отдельный HTTP поверх | Быстрее в разы, надёжнее на перечислении. Лучший для прошивок |
| **FTP** | **не монтируется как ФС** (FTP-папка в проводнике — оболочечное расширение, `System.IO` его не видит) | **переписывать всё**: обходы, копирование, `FileSystemWatcher` на `revision.json`, `.lnk`. 20+ файлов. Нет атрибутов (`ProtectFromExternalEdits`) и атомарного переименования | нет | **Худший из четырёх.** Максимум работы при минимуме выигрыша |
| **Свой HTTP/WebSocket** | всё через API | максимум работы, но правильной: `ISyncTransport` спроектирован под это (`:41-46`), плюс `IFirmwareStore` | лучшая: контроль доступа, стабильные URL, версионирование | Правильный конечный пункт, но отдельный проект на месяцы |

**Рекомендация:** не менять транспорт в рамках этой перестройки. Прагматичный шаг — **SMB для прошивок
(диск 1) + WebDAV или лёгкий read-only HTTP поверх диска 3**. Третий диск отдаётся по HTTP только на
чтение — этого достаточно и для QR, и для телефона наладчика; тяжёлое уходит на быстрый SMB. Код
меняется в одном месте — `VersionLayout.InstructionUrl`.

Правило построения URL должно быть **одно**, и его надо проверить кнопкой «Проверить ссылку» в
настройках (HEAD по собранному URL). Иначе кириллические сегменты дадут битые QR, и обнаружится это на
печатной этикетке в поле.

### Этап 1b и имя файла инструкции сделаны (v1.65.0, 05.08.2026)

Имя файла инструкции — `инструкция_<версия>.<расширение>` (`InstructionNaming`): ставится в момент
укладки файла на диск (`InstructionStorage.Copy`) и правится перестройкой диска
(`DiskLayoutMigrator.OpKind.RenameInstruction` — только в папках «Инструкция» ВНУТРИ версии, в общей
папке контроллера документ принадлежит всем версиям сразу). Приставка «инструкция_», а не голое имя
версии из п. 1 «Целевой раскладки»: рядом с прошивкой, названной по версии, два файла с одинаковым
именем и разными расширениями путают человека.

Заглушка — `InstructionStub` + `App/Services/InstructionStubWriter` (текст рисуется визуалом WPF и
кладётся картинкой через `SimplePdfWriter`, как и планировалось). Имя у неё **то же самое
каноническое** — это и есть «путь не меняется, меняется только файл»: наклейку с QR печатают до
готовности документа, и настоящая инструкция ложится ровно на её место. Раз имена совпадают, заглушка
опознаётся меткой `%ANTARUS-INSTRUCTION-STUB` в конце файла (комментарий PDF после %%EOF), а не по
имени; резолверы документов считают её «не документом» наравне с `.lnk`
(`DocFileResolver.IsNotADocument`), поэтому «инструкция ✓», печать и «редактировать» от неё не
загораются. Единственное исключение — кнопка «QR инструкции»: ей нужен путь, а не документ.

**Не сделано:** этап 2 (реестр `fw_version_files` и модерация с выбором «перенести с предыдущей /
заглушка / без файла»), этап 6 (транспорт), сайдкар `.antarus\files.json`.
