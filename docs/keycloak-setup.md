# Keycloak: что нужно от ИТ и как это подключается к Antarus ПО Finder

Решение принято: боевой Keycloak поднимает ИТ на серверах компании, пользователи приходят
**федерацией из Active Directory** (домен `Elita`) — люди входят теми же доменными логином и
паролем, отдельный список учёток не заводится.

Этот документ — две части: **раздел 1 можно отдать ИТ как есть**, разделы 2–4 — для нас.

Контекст и обоснование, почему именно OIDC, а не SAML — в
[corporate-auth-and-network.md](corporate-auth-and-network.md).

---

## 1. Что нужно создать в Keycloak (для ИТ)

### 1.1. Realm

Отдельный realm под внутренние приложения, например `antarus`. Использовать `master` не нужно и
нежелательно — в нём живут администраторы самого Keycloak.

### 1.2. Федерация Active Directory

`User Federation → Add LDAP provider`:

| Параметр | Значение |
|---|---|
| Vendor | Active Directory |
| Connection URL | `ldaps://<контроллер домена>:636` (или `ldap://…:389`, если LDAPS не разворачивали) |
| Bind type | `simple` |
| Bind DN | сервисная учётка с правом **чтения** каталога |
| Users DN | OU, где лежат сотрудники |
| Username LDAP attribute | `sAMAccountName` |
| Edit mode | **READ_ONLY** — Keycloak не должен писать в AD |
| Import users | включено |
| Sync registrations | выключено |

Дополнительно — `Mappers → group-ldap-mapper`, чтобы группы AD подтягивались в Keycloak. Без него
приложение не сможет отличить администратора от наладчика.

**Единственное, что нужно от ИТ сверх настройки: сервисная учётка с правом читать каталог.** Права
на запись не нужны — режим READ_ONLY.

### 1.3. Клиент для настольного приложения

`Clients → Create client`:

| Параметр | Значение |
|---|---|
| Client ID | `antarus-po-finder` |
| Client type | OpenID Connect |
| Client authentication | **Off** (публичный клиент) |
| Authorization | Off |
| Standard flow | **включён** |
| Direct access grants | выключен |
| Implicit flow | выключен |
| Service accounts | выключен |
| Valid redirect URIs | `http://127.0.0.1/*` и `http://localhost/*` |
| Web origins | оставить пустым |
| PKCE method | **S256** (обязательно) |

**Почему публичный клиент без секрета и с redirect на `127.0.0.1`.** Это стандартная и
рекомендованная схема для настольных приложений (RFC 8252): секрет в программе, установленной на
десятках машин, всё равно не является секретом, а защиту даёт PKCE. Порт в redirect заранее не
известен — приложение слушает свободный порт на localhost, поэтому в списке нужен шаблон `*`, а не
конкретный адрес. Это не открывает доступ снаружи: `127.0.0.1` доступен только с самой машины.

**Почему не встроенный браузер.** Вход открывается в системном браузере пользователя — так работают
уже открытая сессия и многофакторная аутентификация, и приложение никогда не видит пароль.

### 1.4. Передача групп в токен

`Clients → antarus-po-finder → Client scopes → antarus-po-finder-dedicated → Add mapper → By
configuration → Group Membership`:

| Параметр | Значение |
|---|---|
| Name | `groups` |
| Token Claim Name | `groups` |
| Full group path | **Off** |
| Add to ID token | On |
| Add to access token | On |
| Add to userinfo | On |

### 1.5. Доступность по сети

Адрес Keycloak должен быть доступен **с рабочих машин наладчиков**. Это важно с учётом планов по
IPsec и ограничению исходящих соединений списком разрешённых IP: если адрес Keycloak в список не
попадёт, вход в программу перестанет работать — молча и сразу у всех.

### 1.6. Что прислать нам обратно

Пять строк, больше ничего не нужно:

1. Адрес issuer — вида `https://<хост>/realms/antarus`
   (проверяется открытием `https://<хост>/realms/antarus/.well-known/openid-configuration`);
2. `client_id` — `antarus-po-finder`, если назвали иначе — фактическое имя;
3. имя claim с группами — `groups`, если сделали иначе — фактическое;
4. точные названия групп AD, которые означают **администратора**, **наладчика**, **программиста**;
5. подтверждение, что адрес Keycloak доступен с машин наладчиков.

## 2. Что делаем мы

### 2.1. Разработка не ждёт ИТ

OIDC-вход пишется и тестируется против **локального Keycloak в докере**, с тем же realm и тем же
`client_id`. Переключение на боевой — это смена адреса issuer в настройках, код не меняется. То есть
пункт 1 блокирует только боевой запуск, а не разработку.

```
docker run -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  quay.io/keycloak/keycloak:latest start-dev
```

Дальше руками: realm `antarus`, клиент по спецификации из 1.3, пара тестовых пользователей и групп.
Федерацию AD локально не воспроизводим — для приложения нет разницы, откуда Keycloak взял
пользователя.

### 2.2. Куда встраивается

Гейт входа (`AdStartupLoginDialog`, показывается в `App.OnStartup` до главного окна) переводится на
интерфейс `IIdentityProvider` — это отдельная работа, которая уже идёт. OIDC становится второй его
реализацией рядом с нынешней проверкой AD:

```
IIdentityProvider
    Task<IdentityResult> SignInAsync(CancellationToken ct)
        → { UserName, DisplayName, Email, Groups[], ExpiresAt, Success, FailureReason }
```

Поток входа: приложение поднимает временный слушатель на свободном порту `127.0.0.1`, открывает
системный браузер на authorization endpoint с PKCE, получает код на loopback, меняет его на токены,
читает `groups` и отображает их в роль приложения по настраиваемому соответствию.

### 2.3. Что остаётся как запас

Оставляем и **не** выключаем:

- вход по AD (`ldap` / `http` / `both`) — когда Keycloak недоступен;
- аварийный вход паролём администратора;
- кэш сессии «запомнить на N дней».

SSO добавляет ещё одну точку отказа, а у наладчиков в поле сеть бывает какая угодно. Порядок:
Keycloak → при недоступности AD → при недоступности аварийный вход.

### 2.4. Соответствие групп и ролей — решено

Названий групп AD пока нет, поэтому жёстко зашивать нечего. Решение: **настраиваемая таблица
«группа → роль» в настройках приложения**, редактируется администратором, синхронизируется между
машинами вместе с остальными общими настройками (в отличие от адресов, которые per-machine).

Правила, которые закладываем сразу, чтобы потом ничего не переделывать:

- сопоставление **без учёта регистра**, по полному имени группы, плюс отдельная галка «искать
  вхождение» для случая, когда в AD группы называются длинно и с префиксами подразделения;
- если пользователь попал сразу в несколько групп — берётся **бо́льшая** роль (администратор
  сильнее наладчика);
- если ни одна группа не совпала — **минимальная роль, а не максимальная**. Ошибка в сторону
  меньших прав; человек увидит внятное «вход выполнен, но прав не выдано, обратитесь к
  администратору», а не молча получит чужие возможности;
- у роли, полученной из Keycloak, приоритет над ролью, определённой прежним способом (по группам AD
  напрямую) — иначе при переключении на SSO два механизма будут спорить;
- изменение таблицы применяется при следующем входе, а не задним числом к текущей сессии.

Пока ИТ не прислал названия групп, таблица пустая — то есть вход через Keycloak работает, но роль
выдаётся минимальная. Как только названия придут, это одна строка настроек, а не правка кода.

## 3. SAML

Отдельно делать не нужно. Keycloak умеет и OIDC, и SAML одновременно: ИТ настраивает SAML для своих
веб-систем на том же realm, наше приложение работает по OIDC, единый вход при этом сохраняется —
пользователь входит один раз. Реализовывать SAML в настольном приложении напрямую не следует:
он спроектирован под браузерные приложения с серверной частью, которой у толстого клиента нет.

---

### 2.5. Что закладываем «по максимуму», не дожидаясь ИТ

Принцип: всё, что ИТ может сделать иначе, чем мы предполагаем, должно быть **настройкой, а не
кодом**. Тогда подключение к тому, что они в итоге поднимут, — это заполнить поля, а не выпускать
новую версию.

Настройки (per-machine, рядом с адресами домена и сервера проверки — они уже исключены из синхры):

| Настройка | Зачем |
|---|---|
| адрес issuer | `https://<хост>/realms/<realm>` — реалм могут назвать иначе |
| `client_id` | могут завести под другим именем |
| имя claim с группами | `groups` — распространённый, но не единственный вариант |
| включён ли вход через Keycloak | чтобы выкатить код заранее и включить, когда ИТ будет готов |
| порядок способов входа | Keycloak → AD → аварийный, но переставляемо |
| таймаут ожидания входа | под IPsec и медленные каналы |

Заложить в коде, но не привязываться к конкретным значениям:

- **обнаружение конечных точек через `.well-known/openid-configuration`**, а не захардкоженные
  пути — если ИТ поднимет Keycloak за обратным прокси с префиксом в пути, всё продолжит работать;
- **самоподписанный или внутренний сертификат** — вероятный сценарий для внутреннего сервера;
  нужна явная настройка «доверять сертификату этого адреса» с честным предупреждением, а не
  безусловное отключение проверки TLS;
- **обновление токена (refresh)** и корректное поведение при истёкшей сессии — не выкидывать
  человека посреди работы, а тихо продлить, и только при неудаче просить войти заново;
- **выход (logout)** — и локальный, и с уведомлением Keycloak;
- **диагностика в экране «Состояние подключения»**: доступен ли issuer, отвечает ли
  `.well-known`, какая ошибка пришла. Без этого разбор «у меня не входит» превращается в RDP.

Чего сознательно НЕ делаем заранее: SAML в приложении (раздел 3), собственный сервис-посредник,
хранение токенов в чём-то сложнее защищённого файла профиля пользователя.

## 4. Порядок работ

1. ✅ Спецификация для ИТ — этот документ, раздел 1. Можно отдавать.
2. 🔄 `IIdentityProvider` — рефакторинг без смены поведения (в работе).
3. Локальный Keycloak в докере + OIDC-провайдер поверх `IIdentityProvider`.
4. Настройки из 2.5 + таблица «группа → роль» из 2.4.
5. Порядок фолбэка Keycloak → AD → аварийный вход, с внятным показом, что именно не сработало.
6. Переключение на боевой issuer, когда ИТ пришлёт пять строк из 1.6.

Пункты 3–5 не ждут ИТ вообще: пишутся и проверяются против локального Keycloak. От ИТ блокируется
только пункт 6.
