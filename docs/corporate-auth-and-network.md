# Корпоративный вход и сеть: OpenID Connect, SAML, IPsec, ограничение по IP

Заметка «на будущее» — что ИТ планирует со стороны инфраструктуры и что должно быть готово в
приложении, чтобы это не превратилось в переписывание. Кода пока не меняет.

---

## 1. Что есть сейчас

Вход построен вокруг одного интерфейса — `AntarusPoFinder.Core/Services/IAdCredentialValidator.cs`.
Реализации:

- LDAP-бинд к контроллеру домена (`System.DirectoryServices.AccountManagement`);
- `HttpAdCredentialValidator` — проверка через HTTP(NTLM) к `ad_http_url`
  (`https://disk.antarus.su/cloud`);
- `CombinedAdCredentialValidator` — режим `both`: сначала LDAP, при недоступном по сети домене —
  HTTP-фолбэк. Это текущий дефолт (`ConfigService.cs:74`, `AdAuthMode():369`).

Гейт — `AdStartupLoginDialog`, показывается в `App.OnStartup` до главного окна; закрыл окно = вышел
из приложения. Всегда есть аварийный вход паролём администратора. Роль определяется по группам AD.

**Главный вывод: точка расширения уже правильная.** Добавление OIDC/SAML — это ещё одна реализация
`IAdCredentialValidator` (или, точнее, соседний интерфейс, см. ниже) плюс ветка в
`AdCredentialValidatorFactory`. Гейт, кэш сессий, ростер пользователей и определение роли
переписывать не придётся.

## 2. OpenID Connect

**Это реалистичный вариант, и его стоит делать первым, если ИТ будет вводить SSO.**

Ключевое отличие от нынешней схемы: при OIDC приложение **не должно видеть пароль**. Значит
`IAdCredentialValidator` (метод «проверь логин+пароль») для него не подходит по форме — нужен
соседний интерфейс уровня «получи подтверждённую личность»:

```
IIdentityProvider
    Task<IdentityResult> SignInAsync(CancellationToken ct)
        → { UserName, DisplayName, Email, Groups[], ExpiresAt }
```

Существующая AD-проверка становится одной из его реализаций (обёртка над сегодняшним валидатором),
OIDC — второй. Гейт зовёт `IIdentityProvider`, а не валидатор пароля.

**Чем показывать окно провайдера.** В проекте уже подключён `Microsoft.Web.WebView2`
(`AntarusPoFinder.App.csproj`) — встроенный браузер есть, доустанавливать нечего. Но правильнее
использовать не встроенный WebView, а **системный браузер + loopback-redirect** (`http://127.0.0.1:<порт>/`),
authorization code + PKCE: так работает корпоративный SSO с уже открытой сессией пользователя,
работает MFA, и приложение по-прежнему не касается пароля. Встроенный WebView2 многие IdP
целенаправленно блокируют.

**Роли.** Сегодня роль берётся из групп AD. В OIDC группы приходят claim'ом (`groups`, `roles` —
зависит от IdP). Понадобится настраиваемое соответствие «claim → роль в приложении», иначе после
переезда все станут «наладчиками» или все «администраторами».

**Оффлайн.** Гейт обязан продолжать пускать при недоступном IdP: кэш сессии («запомнить на N дней»)
уже есть, аварийный вход админ-паролём тоже. Это не отменяется — наоборот, при SSO становится
критичнее, потому что точек отказа больше.

Объём, грубо: 3–5 дней на провайдера + окно + маппинг ролей, если IdP уже поднят и зарегистрировано
приложение (client_id, redirect_uri).

## 3. SAML

**Для настольного приложения SAML — плохой инструмент, и это надо сказать ИТ прямо.** SAML
спроектирован под браузерные веб-приложения: он передаёт assertion через HTTP POST на сервер
приложения. У толстого клиента такого сервера нет.

Работающие варианты, если ИТ настаивает:

1. **IdP умеет и то и другое** (Keycloak, ADFS, Azure AD, Okta — умеют все). Тогда ИТ настраивает
   SAML для своих веб-систем, а нашему приложению отдаёт OIDC-клиента на том же IdP. Единый вход
   сохраняется, пользователь входит один раз. **Это правильный ответ в 9 случаях из 10.**
2. **Промежуточный сервис**: маленький внутренний веб-сервис принимает SAML и отдаёт приложению
   короткоживущий токен. Это отдельный сервер, который надо поднимать и сопровождать.

Рекомендация: закладываем `IIdentityProvider` (см. выше) — он покрывает оба варианта, потому что для
приложения разница только в том, откуда пришёл токен.

## 4. IPsec

Формулировка была «IPsec на наше приложение, только чтобы работало, поднимала для его работы
драйвер». Разделю на два разных вопроса, потому что ответы разные.

**Приложение не должно и не может само поднимать IPsec-туннель.** IPsec на Windows — это политика
уровня ОС (Windows Filtering Platform / IPsec policy, раздаётся групповой политикой). Приложению
такое не делают: это требует прав администратора на каждой машине, ломается при каждом обновлении
политики и превращает установщик в системный компонент. Правильно: туннель поднимает ОС по GPO,
приложение просто работает поверх.

**Что действительно надо сделать в приложении, чтобы оно жило под IPsec:**

- **Терпимость к «сети ещё нет» на старте.** Туннель поднимается не мгновенно; приложение стартует
  раньше. Сегодня недоступная шара в момент старта — это уже штатная ситуация (весь код писался с
  этой оглядкой), но гейт входа при `ad_auth_mode = both` может упереться в недоступный домен ровно
  в момент, когда туннель ещё поднимается. Нужен внятный повтор («Проверить снова») вместо
  единственного исхода «не вошёл».
- **Таймауты, а не зависания.** IPsec добавляет задержку установления соединения; SMB/WebDAV поверх
  него на первом обращении отвечает секундами. Все походы на шару уже вынесены в фоновые потоки —
  это надо сохранить при любых будущих правках.
- **Диагностика.** Один экран «Состояние подключения»: доступен ли корень диска, доступен ли
  контроллер домена, доступен ли источник обновлений. Без него каждая жалоба «не работает» будет
  разбираться вручную по RDP.

## 5. Ограничение по IP («пропускать только конечные IP»)

Это самое опасное из четырёх пунктов, потому что оно **тихо ломает то, что сейчас работает**.

**Автообновление ходит на GitHub.** `AppUpdateService.cs` — `GitHubOwner = "IlyaRevkin"`,
`GitHubRepo = "antarus-po-finder-dotnet"`, публичные Releases. Если наружу будут выпускать только
перечисленные IP, GitHub из этого списка почти наверняка выпадет (у него нет фиксированного набора
адресов — CDN). Тогда обновления перестанут доезжать **молча**, и это ровно та хроническая проблема,
которая уже была на рабочем ПК.

**Хорошая новость: механизм на этот случай уже есть.** `UpdateSourceKind { Folder, GitHub }` —
приложение умеет брать обновления из сетевой папки, и берёт её в первую очередь, если она указана и
доступна; GitHub используется только как запасной вариант. То есть достаточно:

1. завести на сетевом диске папку обновлений;
2. класть туда `AntarusPoFinder-<версия>.exe` (+ `.sha256`) при каждом релизе;
3. прописать её путь в настройках на машинах.

После этого приложение перестаёт зависеть от доступности GitHub вообще. **Это стоит сделать заранее,
не дожидаясь ограничений — оно уже сейчас чинит хроническую недоставку обновлений.**

Остальные внешние обращения, которые надо проверить до включения ограничений: `ad_http_url`
(`disk.antarus.su`) для HTTP-фолбэка входа, и будущий базовый URL инструкций для QR — если он ведёт
наружу, а QR сканируют телефоном из корпоративной сети, он должен быть доступен именно оттуда.

## 6. Транспорт (WebDAV → FTP / SMB / WebSocket)

Разобрано отдельно и подробно в [hierarchy-rework-plan.md](hierarchy-rework-plan.md), раздел 6.
Коротко:

- **FTP — худший вариант**: не монтируется как файловая система, значит переписывать все дисковые
  операции (20+ файлов), нет атрибутов и атомарного переименования. Не рекомендуется.
- **SMB — лучший для прошивок**: код не меняется вообще, работает быстрее WebDAV в разы.
- **WebSocket / свой HTTP-сервис** — правильный конечный пункт (`ISyncTransport` уже спроектирован
  под подмену транспорта), но это отдельный проект на месяцы, не побочная задача.
- Практичная связка: **SMB для прошивок + read-only HTTP поверх диска инструкций** (нужен для QR).

## 7. Порядок, если браться

1. **Папка обновлений на сетевом диске** — дёшево, механизм готов, чинит существующую проблему и
   заранее закрывает риск ограничения по IP.
2. **Экран «Состояние подключения»** — понадобится и под IPsec, и под смену транспорта, и просто для
   разбора жалоб.
3. **`IIdentityProvider`** — рефакторинг без смены поведения: нынешняя AD-проверка становится одной
   из реализаций. Делается заранее, чтобы появление SSO не было переписыванием гейта.
4. **OIDC-провайдер** — когда ИТ поднимет IdP и выдаст client_id.
5. **SAML** — не делать напрямую; договориться об OIDC на том же IdP.

## 8. Что нужно узнать у ИТ

1. Какой именно IdP планируется (Keycloak / ADFS / Azure AD / Okta / другой)?
2. Дадут ли зарегистрировать desktop-клиента с redirect на `127.0.0.1` (это стандарт для настольных
   приложений, но некоторые ИТ-политики его запрещают)?
3. В каком claim придут группы и как они называются — нужно для соответствия ролям?
4. Останется ли доступ к контроллеру домена по LDAP после введения SSO (это наш оффлайн-запас)?
5. Ограничение по IP — попадёт ли в список GitHub, и если нет, кто и когда кладёт обновления в
   сетевую папку?
6. IPsec раздаётся групповой политикой на все машины или только на часть?
7. Есть ли уже доступная SMB-шара под первый диск, или WebDAV остаётся?
