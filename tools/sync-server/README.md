# antarus-sync — служба обмена каталогом прошивок

Служба Windows, которая отдаёт и принимает общий конфиг Antarus ПО Finder по HTTP. Нужна, чтобы
машины **вне корпоративной сети** видели каталог прошивок: сетевой диск до них не дотягивается, а
без общего конфига такая машина не узнаёт о новых прошивках вовсе — сколько файлов ей ни дай.

Это не файловое хранилище. Служба возит два объекта: маркер ревизии и снимок конфига. Сами
прошивки остаются там, где лежали.

## Что нужно для запуска

**Ничего.** Один файл `antarus-sync.exe`, ~10 МБ. Ни .NET, ни Visual C++ Redistributable, ни
runtime — программа собрана статически и использует только системные библиотеки Windows.
Проверено: в импортах нет ни `vcruntime`, ни `msvcp`, ни `mscoree`.

Разрядность — x64, Windows Server 2016 и новее (как и любая современная Windows 10/11).

## Установка

Положить `antarus-sync.exe` в отдельную папку, например `C:\Program Files\AntarusSync\`, и из
командной строки **от администратора**:

```cmd
antarus-sync.exe install
antarus-sync.exe start
```

`install` регистрирует службу `AntarusSync` с автозапуском и создаёт рядом с exe файл настроек
`antarus-sync.json` — вместе с ключом для первой машины. Ключ показывается в файле, его надо
передать тому, кто будет подключаться.

Проверить, что поднялась:

```cmd
sc query AntarusSync
curl -H "X-Antarus-Key: КЛЮЧ" http://localhost:8443/ping
```

Удалить:

```cmd
antarus-sync.exe stop
antarus-sync.exe uninstall
```

Перед установкой службы полезно прогнать в консоли — видно всё, что происходит:

```cmd
antarus-sync.exe run
```

## Файл настроек

`antarus-sync.json` рядом с exe. **Пути пишутся либо через `/`, либо с удвоенным `\\`** — это
обычное правило JSON, одинарный `\` он считает началом escape-последовательности.

```json
{
  "listen": ":8443",
  "base_path": "/",
  "tls": { "cert_file": "", "key_file": "" },
  "data_dir": "C:/ProgramData/AntarusSync/data",
  "log_file": "C:/ProgramData/AntarusSync/antarus-sync.log",
  "max_body_mb": 64,
  "server_name": "",
  "allowed_ips": [],
  "reject_stale_revision": false,
  "clients": [
    { "name": "admin-revkin", "key": "…", "can_write": true },
    { "name": "naladchik-1",  "key": "…", "can_write": false }
  ]
}
```

| Поле | Смысл |
|---|---|
| `listen` | Порт. По умолчанию `:8443`. Можно указать и интерфейс: `127.0.0.1:8443`, если снаружи её публикует обратный прокси. |
| `base_path` | Префикс пути, если служба живёт не в корне (например `/antarus/`). Обычно `/`. |
| `tls` | Если заданы **оба** файла — служба слушает HTTPS сама. Если пусто — HTTP, и TLS снимает прокси перед ней. |
| `data_dir` | Куда лечь двум файлам обмена. |
| `log_file` | Журнал. Растёт до 8 МБ, потом уезжает в `.old`. |
| `max_body_mb` | Предел размера принимаемого объекта. Без него один запрос забьёт системный диск. |
| `server_name` | Как служба представляется в `/ping`. Пусто — имя машины. |
| `allowed_ips` | Необязательный белый список адресов или подсетей (`10.0.0.0/8`). Пусто — проверки нет. |
| `reject_stale_revision` | См. ниже. По умолчанию выключено. |
| `clients` | Кому разрешено, с каким ключом и с правом записи или без. |

После правки настроек службу надо перезапустить: `stop`, затем `start`.

## Ключи и опознание

Ключ у каждой машины **свой**. Это не формальность: в журнале видно, кто пришёл, и отобрать доступ
у одной машины можно, не меняя ключ остальным.

```cmd
antarus-sync.exe addkey naladchik-2
antarus-sync.exe addkey admin-belyi -write
antarus-sync.exe keys
```

`can_write` — право отправлять конфиг. **По умолчанию его нет, и это осознанно:** снимок каталога
перезаписывается целиком, поэтому одна ошибочная отправка стирает чужую работу. Наладчику снаружи
каталог нужен на чтение — право записи выдаётся отдельно и не всем.

Ключ передаётся в заголовке `X-Antarus-Key`. Не Basic-авторизация: Basic по дороге перехватывает
Windows-редиректор и часть корпоративных прокси, начиная спрашивать логин у человека посреди
фоновой синхронизации.

## Как проверить руками

```cmd
curl -H "X-Antarus-Key: КЛЮЧ" https://адрес:8443/ping
```

Ответ — кто вы для службы и куда слать дальше:

```json
{
  "service": "antarus-sync", "version": "1.0.0",
  "server": "ANT-SRV", "time": "2026-08-20T12:00:00Z",
  "client": "naladchik-1", "can_write": false,
  "revision": 42, "has_config": true,
  "endpoints": { "ping": "/ping", "revision": "/revision", "config": "/config" }
}
```

## Что отдаёт служба

| Метод и путь | Что делает |
|---|---|
| `GET /ping` | Опознание и точки входа (см. выше). |
| `GET /revision` | Маркер ревизии. `404` — маркера ещё нет. |
| `POST /revision` | Записать маркер. Нужно право записи. |
| `GET /config` | Снимок конфига. `404` — снимка ещё нет. |
| `POST /config` | Записать снимок. Нужно право записи. |

**Только GET и POST.** Ни PUT, ни PATCH, ни глаголов WebDAV — их корпоративные прокси режут
регулярно, а отладить такое с рабочей машины почти невозможно. На стороне приложения это
закреплено тестом, здесь — тоже.

Коды ответов: `401` ключа нет или не опознан, `403` машина отключена либо нет права записи,
`404` объекта ещё нет, `409` присланная ревизия не новее лежащей (если включена защита),
`413` тело больше предела, `400` пустое тело.

## Порт и сеть

По умолчанию `8443`. Правило в брандмауэре:

```cmd
netsh advfirewall firewall add rule name="Antarus Sync 8443" dir=in action=allow protocol=TCP localport=8443
```

Два рабочих варианта публикации:

1. **Служба сама слушает HTTPS.** Заполнить `tls.cert_file` и `tls.key_file` (PEM). Подходит,
   когда сертификат есть и его не жалко положить рядом.
2. **Служба слушает HTTP на `127.0.0.1:8443`, наружу её отдаёт IIS/nginx.** Тогда TLS, сертификат и
   его продление остаются там, где ими уже занимаются.

## Про защиту от отката ревизии

`reject_stale_revision` заставляет отклонять маркер, номер которого не больше уже лежащего.

**По умолчанию выключено намеренно.** В первый день семантика службы обязана совпадать с сетевой
шарой один в один, иначе разбирать придётся не «работает ли обмен», а «что изменилось».

Включать стоит потом, и вот зачем. Снимок перезаписывается целиком, а право записи есть у
нескольких администраторов — двое, нажавшие «отправить» почти одновременно, сейчас молча затирают
работу друг друга. С включённой защитой проигравший получит `409` и увидит, что его правки не
уехали, вместо тихой потери.

## Данные и надёжность

Два файла в `data_dir`: `revision.json` и `config.bin`. Служба **не разбирает** их содержимое —
возвращает байт в байт то, что прислали. Шифрование снимка и формат маркера живут в приложении.

Запись атомарная: во временный файл, затем переименование поверх. В снимке лежит весь каталог
прошивок, и обрыв связи посреди прямой записи оставил бы обрезанный файл, который выглядит как
настоящий — и все машины приняли бы его за новый каталог.

Резервная копия — обычным копированием `data_dir`, служба его не блокирует.

## Журнал

`log_file`, по умолчанию `C:\ProgramData\AntarusSync\antarus-sync.log`. Пишутся все запросы с
адресом, методом, кодом ответа и временем, а также все отказы с указанием, чей ключ и почему не
прошёл. При разборе жалобы «не синхронизируется» смотреть сюда первым делом.

## Сборка из исходников

```cmd
cd tools\sync-server
go build -o antarus-sync.exe .
go test ./...
```

Go 1.21 и новее. Единственная зависимость — `golang.org/x/sys` (работа со службами Windows).
